# 多模态 RAG 与视觉文档检索

本文整理自 RAG 课程学习记录，保留其中的解释与理解。

## 多模态 RAG：知识库不只有文字

实际资料常有 PDF、幻灯片、表格和图片。多模态 RAG 的一个常见目标是让用户用文字或图片提问，从图文混合资料中找证据，再输出文本回答。与纯文本 RAG 相比，检索端需要能够处理图文表示，生成端需要能读懂被检索到的图片或页面。

### 多模态 Embedding：把图文放进可比较的空间

多模态嵌入模型可以分别编码文字和图片，使相关的图文表示可比较。用户用文字或图片提问时，也要用与资料向量兼容的方式编码查询。

以一种 CLIP 风格、采用 Vision Transformer 的视觉编码器为例，可以把图片变成向量的过程拆开看。这里讲的是一个教学用的实现路径，并非所有多模态模型都按同一尺寸和步骤处理图片：

1. 缩放和归一化图片，准备模型需要的输入尺寸。
2. 把图片切成 patch；16×16 像素是某些模型的设置，不是统一规定。
3. 将每个 patch 转成向量并加入位置信息。
4. 用视觉 Transformer 让这些局部表示相互交互，学习画面含义。
5. 汇聚图像表示，再投影到与文字可比较的空间。

有些视觉编码器会使用 `[CLS]` 这样的特殊 Token 汇聚图像信息，也有其他汇聚方式。“16×16 patch → 加位置 → 用 `[CLS]` 输出”可帮助理解某类视觉 Transformer，但不是 CLIP 或所有多模态模型的统一规定。

### 视觉语言模型：检索后还要看懂原图

检索库里的向量用于寻找候选；生成模型通常需要拿到候选对应的文本、图片或页面内容，而不是只收到一个检索向量。为了理解生成侧，可以看一类视觉语言模型的过程：视觉编码器先把图片变成多个局部表示，常与 patch 对应；这些视觉表示经过转换后与文字 Token 一起成为模型可处理的输入，模型在两类信息间建立联系，再逐 Token 输出文字。具体模型也可能采用不同的视觉编码与融合方式。

### PDF 与幻灯片为什么需要更细的表示

一整页 PDF 可能同时有标题、正文、图表和表格。若只用一个向量概括整页，细节容易被稀释。传统做法可先识别页面区域并抽取文字、表格或图片，再分块索引；版面复杂时，识别也可能出错。

另一类视觉文档检索方法把页面直接作为图片处理，ColPali 是一个例子。可以这样理解：

1. 将页面图像编码成多个局部表示，而不是只用一个向量概括整页。这样页面上的每个细节都有自己的向量，不会被平均掉。
2. 把这些局部表示作为可检索的多向量记录保存。
3. 查询时，用细粒度的晚交互比较问题与页面的局部区域，再得到页面级相关性分数。

这种方式保留版面视觉线索，也要存储和比较更多向量。patch 划分和向量数量由具体模型决定，不是所有 PDF 都要机械切成“成百上千个均匀方块”，更不能保证一定比抽取文字与版面区域的方案好。

这两条路线的取舍仍然是：能否找回关键细节、版面处理是否稳定、存储和查询费用是否可接受。图文混合文档适合用具有代表性的页面和问题做比较。
