# Agentic RAG 的工作流组织

本文整理自 RAG 课程学习记录，保留其中的解释与理解。

基础 RAG 可以沿着相对固定的“检索 → 生成”路径工作。更复杂的系统可能需要判断资料是否够用、选择知识库、拆分问题或再次检索。Agentic RAG 用有条件的步骤组织这些动作。

## Agentic RAG：让流程按问题需要调整

下图中的评估环节会判断当前检索到的 chunk 是否足以回答问题。若证据不足，流程可改写问题或继续检索；若证据足够，再进入回答生成。其中evaluator LLM : 用于评估目前检索到的chunk是否足以回答当前问题

![图示：Agentic RAG：让流程按问题需要调整](图片附件/Pasted%20image%2020260902210903.png)

可以先把它画成流程图：一个节点负责路由，一个节点负责检索或检查证据，最后的节点合成回答。节点可能由 LLM、规则或专门工具承担，不要求每一步都调用一个大模型。简单判断可以考虑较小模型，复杂生成交给能力更强的模型；引用检查也可以由专门方法负责。这样设计仍需在质量、延迟和费用间权衡。

下面四张图按顺序展示四种组织方式：顺序流程让上一步输出接到下一步；条件流程根据问题选择路径；迭代流程让生成与评估往返；并行流程让多个分支同时工作，最后汇总。图中把许多节点画成 LLM 调用；实际节点也可以是规则或工具。

![图示：Agentic RAG：让流程按问题需要调整](图片附件/Pasted%20image%2020260902211455.png)

顺序图让解析、改写和引用等步骤依次衔接；条件图让路由节点决定走哪条支路。

<img src="图片附件/Pasted%20image%2020260902211630.png" width="440" alt="图示：Agentic RAG：让流程按问题需要调整">

迭代图中的评估结果会回到生成节点，形成多轮修改；并行图则由协调节点分出多条任务，最后再汇总。

![图示：Agentic RAG：让流程按问题需要调整](图片附件/Pasted%20image%2020260902211656.png)

![图示：Agentic RAG：让流程按问题需要调整](图片附件/Pasted%20image%2020260902211753.png)

一个并行流程例子是：复杂问题同时从三个资料库检索，最后由合成环节汇总。并行能缩短相互独立步骤的等待时间；但调用更多模型或工具会提高费用，合成时还要处理结果间的冲突。是否值得并行，需要看真实问题和服务约束。
