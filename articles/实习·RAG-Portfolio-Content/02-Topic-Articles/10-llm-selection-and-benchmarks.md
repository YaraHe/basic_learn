# LLM 选型与评测

本文整理自 RAG 课程学习记录，保留其中的解释与理解。
## 选择 LLM：先看任务，再看模型参数

选择生成模型时，可以从五类特征入手：

1. **模型规模与能力。** 参数量从较小模型到大型模型差异很大。规模可以帮助估计资源需求，但不是回答质量的唯一指标，也不能只按参数量决定成本。
2. **调用成本。** 商业服务常按输入和输出 Token 分别计费，也可能采用实例、时间或其他方式。应按实际调用量估算，而不是只看标价。
3. **上下文窗口。** 一次请求能处理的 Token 总量包括输入消息、检索片段和模型输出。RAG 带入的 chunk 会占用窗口；通常按实际处理的 Token 计费，具体仍以供应商规则为准。
4. **延迟与速度。** 首 Token 延迟衡量用户等到第一段回复的时间；每秒输出 Token 数衡量后续生成速度。这两个值都影响体验。
5. **训练知识时间边界。** 模型不一定掌握训练后发生的事件；RAG 可以提供更新的外部资料。训练截止日期较新可能有帮助，但仍要看任务实测。

模型规模数字容易看错单位：例如 1–10 billion 是约 10–100 亿参数；100–500 billion 是约 1,000–5,000 亿参数。实际候选模型的能力、价格和上下文窗口都需以当时的服务信息核实。

### Benchmark 怎样用于选型

常见评测有三类：自动化任务测试、人类偏好评估、LLM 作为裁判。

自动化任务测试通过各种任务来对大型语言模型进行评分。典型的形式可能是选择题测试。MMLU 是覆盖 57 个学科任务的自动化测试例子。人类偏好评估可以让两个模型回答同一问题，再请人选择更好的回答；LLM Arena（Text Arena）就是非常流行的人工打分排行榜平台。相较于自动化基准测试，。这样的排名来自许多人的相对偏好，而不是只答对几道固定题。

LLM 裁判则让另一个模型按照标准答案或评分规则比较回答。有的评测记录分数，有的通过两两比较统计胜率；“模型裁判”本身并不规定唯一的分数形式。它成本较低、便于扩展，但裁判也可能受提示方式、回答顺序或模型偏好影响，因此重要结论仍需人工核看。

好的测试集要贴近自己的项目。例如保险知识库问答，应纳入保险业务问题，而不能只凭数学题表现选模型。题目还需要有区分度、可多次执行测试，整体结果波动小；输出结果可核验，方便对比版本迭代效果，并尽量预示实际用户体验。若测试题出现在训练数据里，还要警惕数据污染。
