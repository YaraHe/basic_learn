# RAG 从原型到生产：评估、成本与延迟

本文整理自 RAG 课程学习记录，保留其中的解释与理解。

原型能回答几个测试问题，还不等于能稳定服务真实用户。上线后仍需面对多种问题，如何评估应对？

## 生产环境里的四类挑战

1. **扩容与性能。** 用户请求变多，延迟和系统负载可能上升，内存与算力成本也会增加。扩容时仍要维持可接受的响应速度。
2. **用户输入不可预测。** 测试集无法覆盖所有真实提问，系统还会遇到模糊、无关或不符合预期的 Query。
3. **真实资料不整齐。** 元数据可能缺失，内容分散在 PDF、PPT、图片等格式中，需要提取、清洗和建立可检索记录。
4. **安全与隐私。** 检索要遵守文档访问权限；日志和测试集也可能包含用户问题及敏感资料，需要按业务要求控制访问和保存。

## 先建立评估与可观测能力

应对以上提到的挑战，首先需要建立一套完善的可观测系统。
生产系统至少要同时观察**软件性能**和**回答质量**。前者包括延迟、吞吐量、错误率、资源使用和 Token 消耗；后者包括检索是否找到证据、回答是否有用、用户是否满意。只有结果分数而没有请求过程，遇到问题很难定位。

### 聚合统计、详细日志与实验

- **聚合统计**看长期趋势，例如平均延迟、召回率、报错率、平均 Token 消耗。它能提示系统整体变好还是退化。
- **详细日志或 Trace**追踪一条请求：用户问题、检索到的 chunk、送给模型的 Prompt、模型输出、耗时与错误。大盘异常后，可以顺着单条链路找到问题环节。
- 最后，理想的评估系统还应能支持各类实验性操作。如 **A/B 实验**比较配置变动的影响。例如换了检索参数后，同时观察相关性、回答质量、延迟和成本。

日志字段决定以后能做哪些评估：如果没有保留检索片段，就难以回看检索是否找对资料。但应结合隐私要求决定记录范围、脱敏方式和保存期限。

思考追踪的各项指标的一个有效框架就是：范围与评估方式
评估也可从两个维度安排：看**全系统还是单个组件**，以及用**代码指标、人工判断还是 LLM 裁判**。下图可按行和列读：同一个组件既能测延迟，也能检查它给出的内容质量；整套系统则还需要观察用户反馈与最终引用。

人工反馈可以来自点赞、点踩、意见栏和人工标注的测试集。LLM 裁判适合较大规模的质量检查，最好给出明确判定标准；有些问题用“相关／不相关”比随意给 0～100 分更易核验。延迟、吞吐量、内存等软件性能则可以直接用程序记录。

![图示：聚合统计、详细日志与实验](图片附件/Pasted%20image%2020260903101922.png)

对于Software Performance，可以使用code来进行评估。可以轻松获得各个组件及整个系统关于延迟、吞吐量、内存使用情况、每秒生成Token数等数据。

对于Quality Metrics，通常需要借助人工标注或者利用LLM作为评估标准。
对于整个系统的质量，可以通过“点赞点踩”和评论了解
对于单个组件——检索系统，可以整理个人标注的测试数据集来计算召回率、准确率等
对于单个组件——LLM，可以使用基于LLM的评估方法，如之前提到的Ragas，还有像LLM对无关检索信息的忽略程度如何。

以上指标可以通过搭建一个系统来收集，也有许多现成的可观测平台，如开源的由Arise公司开发的Phoenix平台。Phoenix 是一类用于观察 LLM 应用链路的工具示例，可以查看请求 Trace，并接入评估流程。Ragas 指标也可作为外部评估结果接入；Prompt Playground 与实验功能可用于比较不同 Prompt 版本。

组件的 CPU、内存、磁盘或数据库服务指标仍需由相应监控系统补足，不能指望一个 LLM Trace 页面覆盖全部基础设施。Datadog、Grafana 等可用于这类观测；具体集成能力取决于部署方式。

### 从真实请求建立定制评估集

上线后可从真实问题中抽样，逐步建立更贴近用户的评估集：

1. 收集有代表性的用户提问及其回答，并按权限要求处理其中的私有信息。
2. 决定要保存哪些字段。只保存问题与回答，可以做部分端到端检查；若要排查检索或重排，就要保存对应的候选 chunk 和排序结果。
3. 为样本补充人工判断或参考答案，以便反复运行 Recall、回答质量等评估。
4. 定期抽样检查，避免测试集只剩旧问题，无法反映新流量。

真实流量很大，字段越多，存储和隐私管理成本也越高。

## 成本、速度与质量的共同取舍

系统可观测之后，才有条件比较不同配置的收益。更快、更便宜的方案可能损失部分质量；增加一个改写器或重排器，也可能把延迟与费用推高。所以应先找主要成本和慢点，再做有针对性的调整。

### 量化：用较低精度减少占用

量化把模型权重或向量表示中的数值换成更紧凑的形式。例如模型权重可能从 16-bit 表示改为 8-bit 或 4-bit，以降低内存／显存占用和部署门槛；性能收益取决于硬件与实现。精度降低可能影响回答质量，压得越狠，越需要实测。

向量也可以量化，以减少索引与存储开销；一些方案先用低精度向量找候选，再用高精度表示重排。8-bit、1-bit 都是可能的压缩方向，但 Recall@K 会损失多少不能预先保证。

Matryoshka 表示学习提供另一种思路：训练出可按前缀截短维度的嵌入，以较少维度参与检索。它与把数值位宽压低的量化都可能减少占用，但做的不是同一种操作。

### LLM 调用与存储是主要成本项

RAG 的主要费用常来自 LLM 推理／生成，以及向量数据库的存储与查询。降低 LLM 成本可以尝试较小模型、减少不必要的 Agent 路由调用、精简 Prompt、限制返回 chunk 数量和输出长度；若微调后的模型能在特定任务上替代更昂贵的模型，也可以比较其总成本。

高流量时，还可以比较按 Token 付费与租用专用计算资源的方式。Together AI、AWS、Google 等服务提供不同部署选项；哪种更便宜要看流量、利用率、运维负担和当时价格。

向量数据可能放在 RAM、磁盘或对象存储等不同层级。快而贵的存储适合高频索引访问，较慢且便宜的存储适合冷数据或原始文件。

<img src="图片附件/Pasted%20image%2020260903150802.png" width="267" alt="图示：LLM 调用与存储是主要成本项">

可以用“热数据留在更快的介质，冷数据移到更便宜的介质”作为成本设计的直觉：

1. **索引：**某些 HNSW 部署把主要图索引放在 RAM 以追求低延迟；也存在磁盘或混合实现，不能说 HNSW 一律必须完整放在内存。
2. **冷热数据：**高频访问内容可优先放在较快介质，低频向量或相关记录可考虑 SSD 等较便宜的介质，前提是查询体验仍达标。
3. **原始文档：**可以保存在对象存储，向量库保存向量、元数据和文档 ID，检索后再取正文；有些系统也直接保存文本片段，取决于权限、延迟和数据库能力。

### 延迟：先测量哪一段最慢

延迟：指的是单次查询所花费的时间
系统中组件添加越多，延迟就可能越长
因此首先需要了解你的RAG系统可以容忍多大的延迟。
一次 RAG 查询可能经过解析、改写、检索、重排和生成，增加组件通常会增加串行等待，但并行处理也可能缩短总时间。LLM 往往是需要重点观察的环节，实际瓶颈仍要靠 Trace 测出来。

若生成环节慢，可以比较较小或量化模型、减少无效输出；简单路由任务也许不需要大型模型。

![图示：延迟：先测量哪一段最慢](图片附件/Pasted%20image%2020260903173253.png)

还可以对重复问题做缓存：新问题与缓存问题足够接近时，复用已有回答，或用较小模型做少量个性化修改。使用语义缓存时要留意权限、资料时效和“意思相近但答案不同”的问题。


基于Transformers的其他组件包括：Rerank、Query-rewriter、Router LLM。可以先评估每个组件的延迟，再考虑它们提供的增量响应质量。如果获益少，可以调整调用条件或移除该环节。

解决检索侧延迟的方法可以是测试低位向量、分片或数据库提供的索引能力：

- 用量化向量减少存储和计算，再检查召回损失。
- 按地理区域、时间或用户范围分片，缩小单次检索范围；同时注意跨分片查询与维护复杂度。
- 查看数据库内置索引和托管服务是否已经提供所需能力，再衡量引入新组件的收益。

## 从原型走向生产环境：挑战与取舍

从用户问题到最终回答，RAG 不是只有“检索一下再生成”。资料要先被处理、分块、建立索引；问题可能需要解析或改写；检索结果可能需要融合和重排；LLM 需要在有限上下文里使用证据；上线后还要持续看质量、延迟、费用和权限。每增加一项技术，都要回到具体资料和问题，判断它是否真正改善了这条链路。下图重点汇总原型进入生产环境后，流量、故障、质量、成本、延迟、安全与多模态资料带来的挑战。
