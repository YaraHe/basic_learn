# 查询改写、实体识别与 HyDE

本文整理自 RAG 课程学习记录，保留其中的解释与理解。
文档如何切分只是检索的一端，另一端是用户怎样提问。用户问题可能很短、口语化，或者包含需要单独识别的人名、日期和地点。查询处理先理解并改写问题，再交给检索器；重排序则在粗筛后重新判断候选片段是否真的有用。

## Query Parsing 与 Query Rewriting

Query Parsing（查询解析）识别问题中的意图、实体和限制条件。Query Rewriting（查询改写）会把原问题改写成更适合检索的表达方式，有时用 LLM 完成。改写的目标是保留用户原意，同时补足检索所需的关键词或表达方式；改错意图反而会把检索带偏。

### Named Entity Recognition：从问题中提取实体

命名实体识别（NER）可以识别人名、地名、日期等信息。提取后有两种常见用法：一是把实体补进检索表达式，帮助精确匹配；二是把实体映射到可靠的元数据字段，作为过滤条件。能否用于过滤，取决于知识库是否有对应字段，且实体识别是否准确。

GLiNER 是一个可按指定类型识别实体的模型示例：给它问题，并告诉它想找“人物”“日期”等类别，再取得标注结果。

## HyDE：先生成一份“可能的文档”再检索

HyDE（Hypothetical Document Embeddings，假设文档嵌入）先让 LLM 根据问题生成一段可能回答问题的假设文档，再给这段文字生成向量，用它去检索真实知识库。检索回来的仍是真实文档，假设文本只用来引导寻找。

![图示：HyDE：先生成一份“可能的文档”再检索](图片附件/Pasted%20image%2020260831142934.png)

为什么多绕一步？用户可能只问一句很短的话，知识库却用长段落讲解。假设文档可以提供更接近资料写法的检索线索，让向量搜索更容易找到相关区域。但生成内容可能跑偏，也要多一次 LLM 调用，增加延迟和成本。 不是所有场景都变好，长的、描述很充分的用户 query，用 HyDE 收益很小。同时它并非所有短问句都有效，更不能把假设文档当作事实答案；适不适合专业知识库要用具体问题验证。
