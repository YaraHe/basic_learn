# Agent 模式：从 Single-Agent 到 Multi-Agent 编排

本文聚焦一个核心问题：**Agent 有哪些典型的推理与编排模式？它们分别解决什么问题，又有什么优缺点和适用边界？**

## 一、为什么需要了解 Agent 模式？

一次普通的 LLM 调用，通常是“用户输入 → 模型 → 最终答案”。问答、改写、总结等任务，往往这样就能完成。真实业务却可能要连续做几件事：如电商客服处理退款，需要分析诉求、查询订单、判断规则，再决定是否执行退款；编程 Agent 要分析代码、修改、运行测试，并根据报错再次修改；企业 Copilot 可能要查 CRM、知识库和数据库，调用业务 API，然后根据返回结果决定下一步。

这些任务的难点不只是模型会不会回答，还包括：**这一步做完以后，该做什么？是否需要工具？工具返回的结果如何影响下一步？什么时候结束？** Agent 模式讨论的正是这类决策与控制问题。

可以先用一个通俗的比喻理解 Agent 系统：**模型像“大脑”**，负责理解信息并提出下一步；**工具像“手脚”**，让系统能查询或执行外部操作；**编排层像“中枢”**，串联模型、工具、任务状态、循环和终止条件。比喻有助于记忆，但真正调用工具、保存状态和限制执行次数的仍是程序；模型生成了行动意图，不等于行动已经完成。

这份笔记先看一个 Agent 如何完成任务，再看多个 Agent 如何分工和转移控制权。下文选取 ReAct、Plan-and-Execute、Reflexion 三种单 Agent 方法，以及 Supervisor、Workflow、Handoff、Council 四种编排方式作比较。它们是这里讨论的典型方法，并不是 Agent 设计的穷尽分类；多 Agent 系统中的某个子 Agent，内部仍可以采用 ReAct 等单 Agent 方法。

## 二、一个 Agent 如何完成任务？

### 1. ReAct：边判断、边行动、边观察

ReAct 把 **Reason（推理）** 与 **Act（行动）** 交替组织起来。Agent 看当前任务与已有信息，决定下一步要做什么；如果需要工具，就发出调用请求；程序执行工具后，把结果作为 Observation（观察）送回模型；模型再基于新结果判断。这个过程可以概括为：

> Thought（思考） → Action（行动） → Observation（观察） → 再次判断，直到可以给出最终答案。

它像“走一步、看一步”：不要求开始时把完整路线写死，但每走一步都要看外部结果。这也说明 Agent 为什么能“思考 → 行动 → 再思考”：**模型能力、提示词、工具定义和编排代码共同形成循环**。仅有提示词中的“请使用工具”，并不会让工具自动运行。

下图示例提示词让模型使用 `<task>`、`<thought>`、`<action>`、`<observation>`、`<final_answer>` 等标签表达任务、下一步和结果；又给出可用工具、参数格式和停止生成等待真实工具结果的要求。这里的 XML 风格标签是**这份示例为了让程序识别输出而采用的约定**，不是所有 ReAct 或工具调用系统都必须使用的统一格式。

![课程截图：ReAct 示例的系统提示词与输出标签](图片附件/Pasted%20image%2020260726203910.png)

再看可用工具的描述：这张截图列的是文件读取、写入和终端命令，属于一个需要操作文件的示例；下一张图中的高度查询、食谱搜索则使用了别的示例工具，不应误认为同一套工具清单。模型需要知道工具能做什么、需要哪些参数，才可能提出合适的调用；真正允许执行哪些命令、能访问哪些文件，则由应用控制。截图还特别要求模型发出 Action 后等待真实 Observation，不能自己编造工具执行结果。

![课程截图：ReAct 示例的工具列表与执行约束](图片附件/Pasted%20image%2020260726203949.png)

具体例子能把这几个标签连起来。问“埃菲尔铁塔有多高”，模型先提出查询高度的 Action，收到结果后再组织答案。另一个例子要找番茄炒蛋食谱、同时检查冰箱里是否有西红柿；找到食谱并不等于任务完成，还要根据第二次工具结果继续判断。以上这些是课程中展示循环用法的示例。

![课程截图：单次查询与多步工具调用示例](图片附件/Pasted%20image%2020260726204240.png)

下图把用户、Agent 主程序、模型、工具分开：主程序请求模型，收到下一步 Action 后调用对应工具，再把执行结果送回模型；如果模型给出最终答案，就停止循环并回复用户。图中的“重复 n 次”需要程序设置终止条件。**模型负责提出下一步，主程序负责真正执行、记录结果和决定循环是否继续。**

![课程图：ReAct 的模型、主程序与工具之间的循环](图片附件/Pasted%20image%2020260726221613.png)

**它的好处是什么？** 每一步可以利用最新工具结果调整路线，适合智能搜索、工具型 Copilot、开放式知识任务和多轮信息查询。若系统记录了行动与观察轨迹，开发者也比较容易定位哪一步选错了工具、参数或信息。

**代价在哪里？** 只盯当前一步可能忽略整体目标，反复请求同一工具也可能造成无效循环，因此通常要限制轮次并检查进展。模型选错工具或参数，后续判断也会受影响。课程中的文本标签方案还依赖输出格式能被解析；格式不符合约定时，程序要处理错误。这个限制属于该示例的解析方式，不能推广成所有工具调用接口都必须显示 Thought/Action 标签，也不能把可见“思考”当作所有系统的调试前提。

当任务很长、步骤之间有依赖关系时，“每次只想下一步”可能不够稳妥，于是可以先考虑整体计划。

### 2. Plan-and-Execute：先规划，再按结果执行与修订

Plan-and-Execute 的基本思路是：**先把任务拆成有顺序的步骤，再逐步执行；得到新信息后，检查原计划是否仍合适。** 它针对的是 ReAct 在较长任务中可能出现的局部短视：每一步都重新决定方向，可能忘记整体目标、重复执行或弄乱顺序。LangChain 的 Plan-and-Execute 实现提供了“计划者—执行者—重规划”的清晰例子，但这些组件的分工属于一种实现安排，不能据此断定这一思路只由某个框架提出，或每套系统都必须分成三个独立模型。

可以把角色理解为：

- **Plan 模型**先把用户问题拆成有序子任务。
- **Executor（执行 Agent）** 接收当前步骤，调用必要工具取得结果；它内部也可以运行 ReAct 循环。
- **Re-Plan 模型**根据新结果判断还缺什么、计划要不要改，或任务是否已经完成。
- **Agent 主程序**保存计划与历史执行结果，把信息送给相应角色，并控制整个循环。

Plan 与 Re-Plan 可以由同一个模型承担，也可以分开。关键不在角色名字，而在于**新的执行结果会进入下一次决策**；否则初始计划即使写得完整，也可能无法适应中途得到的信息。

#### 课程中的网球查询：计划如何一步步缩短

课程例子的问题是“今年澳网男子冠军的家乡在哪里？”截图把“今年”放在示例运行时点理解。它用于说明怎样根据工具结果改写计划；以下人物、日期和地点均按课程截图复述，不把它当作当前赛事资料。

最初的计划有三步：**查询当前日期 → 查询对应年份的澳网男子冠军 → 查询这位冠军的家乡**。总览图中，主程序先请 Plan 模型产出计划，再把第一步交给执行 Agent；取得结果后，将结果送入 Re-Plan，决定下一步是继续执行还是回答用户。

![课程图：Plan、Re-Plan、执行 Agent 与主程序的数据流](图片附件/Pasted%20image%2020260726224325.png)

**第一步完成后**，执行记录得到示例日期“2025 年 7 月 10 日”。原计划里模糊的“今年”于是可以换成“2025 年”。主程序把用户问题、当前计划和已得到的日期结果交给 Re-Plan；新的待执行计划聚焦于“查询 2025 年冠军，再查其家乡”。第一步不再重复做，但它的结果会保存在历史记录中供后续判断。

![课程图：得到日期后，计划从三步调整为两步](图片附件/Pasted%20image%2020260726223223.png)

**第二步完成后**，示例执行结果给出冠军姓名 Jannik Sinner。主程序将这条结果加入历史执行记录，再把用户问题、更新后的计划与已有结果送给 Re-Plan。这一次无需再查年份或冠军；第三个计划只留下“查询 Jannik Sinner 的家乡”。图中左下角的记录使新计划能够直接引用刚查到的人名。

![课程图：得到冠军姓名后，计划只剩查询家乡](图片附件/Pasted%20image%2020260726223739.png)

**第三步完成后**，截图中的结果是“意大利圣坎迪多”。执行 Agent 把结果交给主程序，主程序加入历史记录，再让 Re-Plan 对照原问题判断：日期、冠军、家乡这条信息链已经走完，可以返回最终答案，而不需要继续生成第四个执行步骤。这个例子展示了“计划 → 执行一步 → 更新历史 → 重规划或结束”的完整闭环。

![课程图：第三步结果写入历史，重规划器判断可以结束](图片附件/Pasted%20image%2020260726223954.png)

**适合什么时候用？** 当任务有较多步骤、步骤之间存在依赖，而且大体能预先拆解时，计划能提供全局视角，也方便审查每一步是否需要人工批准。规划模型与执行模型可以分工：在某些实现里，较强模型负责计划，较轻模型负责部分子任务，有机会降低成本；实际费用仍取决于重规划次数、上下文长度和模型选择，不能仅凭架构名称判断更省 Token。

**需要付出什么？** 规划本身增加调用和等待时间；初始计划如果漏了关键步骤，必须靠后续结果和重规划纠正；保存状态、判断何时重规划也增加了系统复杂度。高度探索式、执行路径难以提前判断的任务，强行先写完整计划可能产生无效工作。图中的每步重规划很适合教学展示，但真实系统不一定每执行一步都要重新规划。

### 3. Reflexion：把一次失败变成下一次尝试的提示

ReAct 主要解决“眼下做什么”，Plan-and-Execute 增加“整体怎样安排”。如果任务做完却失败了，接下来还要回答：**哪里出错？下一轮如何避免同样的错误？** Reflexion 处理的就是多次尝试之间的反馈利用。

它把失败后的分析写成自然语言反思，放入情景记忆缓冲区，让 Actor 在下一次尝试时读到。论文把这种做法称为 *verbal reinforcement learning*：这里的“强化”来自反馈文本对后续决策的影响，并不是训练过程中更新模型权重，仅通过语言反馈实现“轻量级强化学习”。

课程中的四个角色可以这样连起来：

1. **Actor（执行者）** 尝试完成任务，产生行动轨迹；执行方式可以是 ReAct 一类的循环。
2. **Evaluator（评估者）** 检查结果或轨迹，给出成功、失败或其他反馈。反馈可以来自明确规则、测试，也可以由模型参与评判；能否信任反馈仍要看评估标准。
3. **Self-Reflection Model（自反思模型）** 对照失败轨迹和反馈，找出可能出错的决策点，尝试把失败经验提炼成可复用的原则，并把下一轮可执行的改进写成自然语言。
4. **Episodic Memory（情景记忆）** 保存这些反思文本，供 Actor 下一次尝试时读取。

于是流程不是“失败后原样再跑一次”，而是：**Actor 执行 → Evaluator 评估 → 若失败则产生反思并保存 → Actor 带着反思重新尝试**，直到成功或达到次数上限。它尤其适合有自动测试、明确成功条件、允许多次尝试的 AI Coding、数据处理或复杂推理任务。它的价值在于把失败转化为下一轮可用的信息；但如果评估本身不可靠，反思也可能把错误方向写进记忆。

代价同样明显：每轮尝试都可能重新运行 Actor、评估和反思，增加调用次数与延迟；读入累积反思还会占用上下文。适合以更多时间和成本换取改进机会的任务，不适合把一次即时回答硬改造成反复试错流程。

## 三、ReAct、Plan-and-Execute、Reflexion 怎么选？

三者解决的问题不同。下面把关键差异放在一起看；其中“Token、延迟、控制力”的高低只是**在所描述流程下的定性判断**，不是实测排名。一次任务会调用多少工具、是否重规划、最多重试几轮，都可能改变实际成本和速度。

| 维度 | ReAct | Plan-and-Execute | Reflexion |
| --- | --- | --- | --- |
| 首要问题 | 下一步做什么？ | 整体怎么做、如何按结果调整？ | 上次为什么失败、下次如何改？ |
| 决策方式 | 每一步依据当前观察决定 | 先有显式计划，再执行与必要的重规划 | 一次尝试后评估、反思，再尝试 |
| 计划 | 可以边做边形成，不要求完整预设 | 有显式 Plan | 取决于 Actor，可与其他规划方法组合 |
| 动态调整 | 收到工具结果后调整下一步 | 根据执行结果更新剩余计划 | 根据反馈和反思改变下一轮策略 |
| 主要保留的信息 | 当前上下文、工具观察 | 计划、已完成步骤及其结果 | 失败轨迹、反馈与反思记忆 |
| 失败处理 | 在当前循环继续判断或结束 | 修订计划、重试步骤或结束 | 显式分析失败原因，形成下一次尝试的提示 |
| 多轮尝试 | 可以，但不是定义要求 | 可以，但不是定义要求 | 跨尝试迭代是核心机制 |
| 示例组件 | 模型、工具、Agent 循环 | Planner、Executor、Re-Planner | Actor、Evaluator、Reflection、Memory |
| Token 与调用成本 | 随行动轮数增长 | 需计入规划及重规划；分层模型可能改变成本 | 多次尝试通常增加调用和上下文成本 |
| 延迟 | 受工具轮数影响 | 受规划、执行与重规划轮数影响 | 受尝试、评估和反思轮数影响 |
| 可控性 | 能限制工具和轮数，但行动路径动态 | 显式计划便于审查，仍要处理偏离 | 可设置评价与次数上限，结果依赖反馈质量 |
| 适合 | 实时结果决定下一步的任务 | 可大体拆解的长链路任务 | 有可用反馈、允许多次尝试的任务 |
| 核心优势与代价 | 灵活；可能局部短视或循环 | 有全局视角；规划与状态管理更复杂 | 能利用失败经验；试错成本更高 |

这些方法可以叠加，而不是只能三选一。例如先用 Plan-and-Execute 制定整体路线，让 Executor 在某一步内部用 ReAct 查询与行动；如果整次任务未达到检查标准，再由 Reflexion 总结失败原因，供下一次尝试。下面的流程说明：**规划、当前行动、跨尝试改进处在不同层次**。

```text
Plan-and-Execute：制定整体计划
          ↓
Executor：执行当前步骤，内部可以使用 ReAct
          ↓
评估结果；如果未达到目标
          ↓
Reflexion：形成反思，指导下一次尝试
```

## 四、多个 Agent 如何分工与转移控制权？

一个 Agent 承担太多职责时，提示词和工具清单可能越来越长，专业任务互相干扰，权限边界及错误定位也更难管理。此时可以考虑拆成多个有明确职责的 Agent。不过，**多 Agent 并不是默认更好**：增加角色也会带来通信、状态同步、成本和调试问题。设计时更值得先问：任务确实需要分工吗？分工之后，**下一步由谁决定、结果由谁汇总、控制权由谁持有？**

### 1. Supervisor：由总管分派与汇总

Supervisor 像一个总管。下图中，上方的 Supervisor 接收任务并决定让查询、分析、撰写等 Worker 做什么；Worker 返回结果后，再由 Supervisor 判断下一步和组织最终回答。这与“中央协调者动态分配子任务并汇总结果”的思路相近。是否把 Worker 实现为独立 Agent、是否给它们单独记忆、是否允许 Worker 之间直接交流，都属于具体系统设计，不能从 Supervisor 这个名称推断出统一规定。

![课程图：Supervisor 向查询、分析、撰写 Agent 分派任务并接收结果](图片附件/Pasted%20image%2020260821172233.png)

在图示实现中，Supervisor 负责理解任务、拆解、选择 Worker、分配工作、根据返回结果继续调度，最后汇总；Worker 负责各自的专业子任务。这里的 Worker 可以各有系统提示词、记忆和专用工具集，让查询 Agent、分析 Agent、撰写 Agent 专注不同工作；这些是图示方案的角色配置，不是所有系统的硬性要求。如果希望所有重要决策都经过总管，这样做也便于集中记录调度路径、在关键处加入人工审核。

它的优势是职责较清楚：每个 Worker 可以只配与自身任务有关的工具和提示词，方便单独测试与迭代。扩展新能力时，也可以新增专门 Worker，但仍需让总管知道何时调用它、如何处理结果，不能保证“只加 Worker 而完全不用改总管”。

代价是总管可能成为瓶颈或错误来源。选错 Worker、误解返回结果，都可能使后续任务偏离；Worker 多了，总管的能力描述与决策负担也会增加。在课程图这种集中中转的安排下，Worker 间信息经过 Supervisor，会增加传递和上下文成本。它适合需要多种专业能力、且希望有清晰统一调度入口的任务；任务很简单时，额外设置总管未必划算。

### 2. Workflow：由预设流程控制顺序和分支

另一种做法是先把路线设计好，由编排代码按规则连接各步骤，而不是每走一步都请模型自由决定下一个 Agent。这种可以称为 Workflow：输入进入第一个节点，节点输出写入状态，编排层再把需要的数据交给后续节点，直到形成结果。节点可以是 Agent，也可以是规则、工具或普通程序；因此 **Workflow 不天然等于“多个独立 Agent 串行接力”**。

![课程图：预设工作流中的分类、分支、并行与汇总](图片附件/Pasted%20image%2020260821172323.png)

注意图中的顺序：先分类，再根据预设逻辑分支；有些分支中的任务可以并行，最后汇总和格式化。它仍是预设的工作流，因为“何时分支、哪些步骤能并行、如何汇总”是事先设计好的控制规则。分类结果可以由模型产生，路由规则可以由程序执行；关键是不要把图中的分支、并行误说成只能走一条固定的纯串行链。

这样的方案适合步骤大体已知、需要日志、审计或人工审批的业务。节点职责明确，可以单独测试，也容易定位是哪个环节出错。代价是路线越固定，对未知情况的适应性越弱；新业务出现时要调整流程。串行步骤的耗时会逐步累加，前面步骤的错误也可能传给后面；并行分支能缩短一部分等待，但仍须考虑最后汇总与最慢分支。高度探索式、无法事先定义有效路径的任务，可能更需要动态决策。

### 3. Handoff：把当前控制权交给另一位专家

Handoff 强调的不是总管分派子任务后仍持有回答权，而是**当前 Agent 判断应由另一位专家接手时，发出交接请求，让目标 Agent 成为新的活跃执行者**。例如客服初始 Agent 遇到退款问题，把后续处理交给退款专家；专家也可以在规则允许的范围内再次交接。在这里讨论的安排中，每个专家有自己的系统提示词和工具集，并配置可移交的目标列表，不能任意转给未知角色；专家内部仍可使用 ReAct。它与 Supervisor “调用 Worker 完成一个有界子任务、再由总管继续”形成了直观区别。

按这个示例，流程可读作：

1. 用户请求进入初始 Agent；它先处理自己能处理的部分，也可能使用普通工具。
2. 当任务需要另一专业角色时，它提出一个交接请求，例如 `transfer_to_target_agent`。
3. 编排层验证请求和目标，切换当前活跃 Agent，并传递接手任务所需的信息。
4. 目标 Agent 继续处理，可以在允许时再次交接；完成后回答，或由程序按轮次、规则等条件终止。

`transfer_to_target_agent` 是这个示例中的工具名，不是所有框架固定的 API。交接时把完整对话历史传给下一个 Agent，可以是某个实现的默认行为，却不是 Handoff 的定义要求。实际可按任务和权限筛选、摘要或限制交接信息，避免无关内容或敏感数据被无条件传递。OpenAI Agents SDK 的交接机制就提供了输入过滤选项。

它适合客服会话、跨专业咨询等“接下来应由哪位专家直接继续与用户互动”的场景：不必预先写死所有路线，也不用让用户从头复述已经传过去的必要背景。相应代价是路由判断可能出错，Agent 之间也可能来回移交；链路长时，日志、权限和上下文管理更复杂。若需要把同一任务拆给多位专家并行完成、再统一汇总，单纯串行交接通常不是最直接的方案。

### 4. Council：多方独立分析，再汇总差异

这里把“多个 Agent 面对同一问题，分别给出观点，再由汇总者综合”的方式称为 Council（议会模式）。下图中，问题被送到多个 Agent，它们各自生成分析，再进入 Aggregator；汇总可以是比较、合并、进一步讨论分歧或投票。图中不同模型名是示例配置，并非 Council 的必要条件；这个名称也不表示所有框架都有同名标准组件。

![课程图：同一问题交给多个 Agent，再由 Aggregator 汇总](图片附件/Pasted%20image%2020260823184112.png)

多个观点的价值在于**有机会暴露分歧、盲区或不同的判断依据**。例如方案评审、风险评估、内容审核、研究分析、法律审查和代码安全审计等任务，可以让不同角色检查不同问题，再由人或汇总 Agent 看哪些结论一致、哪些需要继续核实。不过，多个 Agent 给出相近答案不自动证明答案正确；研究在特定多 Agent 辩论设置中观察到，Agent 可能相互附和，削弱独立纠错。 尤其在高风险业务中，应依据任务风险核对证据、设置明确的评审标准，并安排适当的专业人员与人工复核；不能只因采用多 Agent 就断定幻觉一定减少或可靠性一定提高。

成本方面，多位 Agent 会增加总调用量和 Token 用量；若能并行执行，总等待时间不一定按人数成倍增加，通常还要等最慢的成员与最后的汇总步骤。汇总者本身也可能识别不了各方矛盾。因此适合确实需要多视角复核、且愿意承担成本的任务；简单问答不必机械使用。

## 五、把四种编排方式放在一起看

课程最后的图把四种方式按“谁决定下一步、灵活性、确定性、适用任务”并排展示。图中的“高、中、低”是帮助比较的概括，并非测量值。读图时先看**控制权**：Supervisor 由总管动态分配；Workflow 由预设流程决定；Handoff 由当前 Agent 在可交接范围内转移；Council 让多方先各自处理，再由汇总机制形成结果。

![课程图：Supervisor、Workflow、Handoff、Council 的定性对照](图片附件/Pasted%20image%2020260823125459.png)

真实系统未必只选一种。以智能客服为例，可以作一个**方案设想**：Supervisor 先判断顾客意图；对于步骤固定的诉求，转入 Workflow；如果某个环节需要多方审查，再引入 Council 来比较不同判断。执行具体节点的 Agent 仍可能在内部使用 ReAct。这个例子说明不同控制方式可以嵌套，并非已部署或验证的产品方案。

因此，设计 Agent Architecture 时，与其问“哪种模式最先进”，不如先问：任务结构是否清楚？下一步需要动态决策吗？是否要拆分权限和专业职责？错误的代价是什么？对延迟、Token 成本和审计有什么要求？这些条件决定应该从简单调用、单 Agent 循环、预设工作流，还是多 Agent 协作中选择什么组合。
