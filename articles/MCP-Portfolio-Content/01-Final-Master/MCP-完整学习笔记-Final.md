# MCP：从统一工具连接到 Cline 配置与调用流程

这份笔记以[原课程视频](https://www.bilibili.com/video/BV1AnQNYxEsy/?spm_id_from=333.1387.0.0&vd_source=268c38babf5f467dc5a0dd934740c944)为主要学习材料，先理解 MCP 为什么出现，再沿着 Windows 上的 Cline 配置示例，追踪一次工具调用怎样在模型、客户端和服务器之间流转。配置界面和命令保留课程示例的语境；协议机制与客户端的具体做法会分别说明。

## 1. MCP 是什么？MCP Server 又是什么？

MCP 是 Model Context Protocol（模型上下文协议）。可以先把它理解为一套约定：支持 MCP 的应用，用共同的消息格式与外部能力对接，不必为每个工具各自发明一套连接方式。不过，MCP 不只涉及“模型调用工具”，服务器还可以提供资源和提示词；本篇主要围绕原笔记着重讨论的**工具**来理解。

这里容易把几个角色混在一起：
**模型**负责理解请求、生成回答或提出工具调用意图；
**宿主应用**（如课程里的 Cline）负责与模型交互、管理连接和权限；
宿主里的 **MCP Client** 负责按MCP协议和某个 **MCP Server** 建立连接、收发消息；
Server 则把天气接口、本地文件、数据库等能力按协议暴露出来。课程把 Server 比作“标准化工具箱”，这个类比有用，但实际调用、展示结果和用户授权仍由应用协同完成。

课程里运行的 Server 是本地程序，常见示例用 Node.js 或 Python 编写；这不是 MCP 对服务器位置和语言的限制。服务器也可以是远程服务。

## 2. MCP 解决了什么连接问题？

### 2.1 从传统工具适配的麻烦说起

没有共同的连接约定时，应用要把某个工具接给模型，通常需要自己处理工具描述、参数、调用、结果转换等环节。再接一个新工具，往往又要写一组类似的适配逻辑。课程用下面这张图说明：用户向模型提出需求，但真正访问外部 API 的是应用中预先写好的调用代码。

![传统工具调用中的应用适配层](图片附件/Pasted%20image%2020260726104203.png)

如果客户端和外部服务越来越多，适配关系也会变复杂。下图的多条连线就是这一问题的**结构示意**。

<img src="图片附件/Pasted%20image%2020260725105558.png" alt="没有 MCP 时多个客户端与外部服务的连接示意" width="323">

四种成本：增加工具要写连接代码；切换模型或模型 API 可能需要调整接口；工具清单若写死在程序里，更新可能牵涉修改或重载；数据从哪里经过，也影响隐私判断。这些问题的程度取决于原有应用如何设计，并非“换模型就必须重写全部适配代码”或“新增工具必然重启整个系统”。MCP 主要针对的是**应用与外部能力之间缺少统一接口**这一层。

### 2.2 MCP 把哪一段连接标准化？

课程中的本地示例是：应用通过 MCP 与几个服务器分别连接，服务器再访问浏览器、文件、数据库或代码仓库。图上出现的 `stdio` 和 `tools/call`，分别指本地进程通信方式和工具调用消息；它们解释了“统一接口”落在什么地方。这张图展示的是**本地 stdio 方案**，MCP 也支持远程连接。

![应用通过本地 MCP Server 连接多种外部能力](图片附件/Pasted%20image%2020260726104431.png)

应用可以按相同协议发现不同服务器暴露的工具，并通过协议调用它们。于是开发者不必为每个客户端与工具组合单独设计一套消息格式。下图把改进前后的连接关系放在一起，重点看中间有没有形成共同接口。协议互通降低重复适配的可能性，但“写一次就能在所有客户端直接使用”还取决于客户端支持、服务器配置、权限和具体能力。

![没有 MCP 与使用 MCP 后的连接关系对比](图片附件/Pasted%20image%2020260725105637.png)

另一个好处是**发现工具**：客户端连接后可请求服务器的工具列表，不必把所有工具定义永久写死在应用代码中。若服务器运行中改变工具列表，协议还提供通知机制；能否立即反映到当前对话，要看服务器是否声明相关能力，以及客户端是否刷新。



## 3. 用 Cline 在 Windows 上配置 MCP Server

以下是原课程用 **VS Code + Cline + Windows** 展示的操作过程。它帮助理解“服务器从哪里来、配置写在哪里、客户端如何启动它”，并不等于所有 MCP 客户端都采用同样的界面或文件位置。实际操作时，以所用客户端和服务器的当前文档为准。

### 3.1 准备客户端和运行环境

| 准备项 | 在这个示例中的作用 |
| --- | --- |
| [VS Code](https://code.visualstudio.com/) | 安装并打开 Cline 扩展的编辑器。 |
| Cline 扩展 | 在侧边栏与模型对话、管理 MCP Server。 |
| 模型提供方、API Key、模型 | 在 Cline 设置中配置，以便它能与模型交互。 |
| Node.js | 运行下面的 `npx` 文件服务器或 Node.js 源码示例。若使用 Python 或远程服务器，应按对应服务器说明准备环境，而不是一律安装 Node.js。 |

### 3.2 先获得一个 MCP Server

原笔记给出三条路径，它们解决的是同一问题：**让 Cline 知道要启动或连接哪个服务器**。

1. **在客户端提供的服务器列表或市场中安装。** 如果所用版本提供这样的入口，可以由界面辅助添加配置。仍要核对将被调用的程序、权限和需要的凭据。
2. **用 `npx` 启动发布好的包。** 课程以文件服务器为例：

   ```text
   npx -y @modelcontextprotocol/server-filesystem D:/项目目录
   ```

   末尾路径是打算开放给这个文件服务器访问的目录，例如改成 `D:/code/work`。它应是真实存在、确实愿意授权的文件夹。`npx` 的便利是不用手动克隆源码；运行时仍可能下载或使用缓存中的包。原课程的命令作为示例保留，具体包及参数以服务器说明为准。

3. **获取源码后在本机运行。** 例如先建 `D:/mcp-tools`，在终端切换到该目录，再运行课程中的占位命令：

   ```text
   cd D:/mcp-tools
   git clone https://github.com/xxx/git-mcp-server.git
   cd git-mcp-server
   ```

   `xxx/git-mcp-server` 是教学占位地址，不是已经核实存在的仓库。克隆源码本身需要网络；“本地运行”不意味着从获取到运行的全程离线。进入实际项目目录后，按该仓库的说明安装项目依赖：Node.js 项目可能用 `npm install`，Python 项目可能用 `pip install -r requirements.txt`。装过 Node.js 运行环境，并不等于装过每个项目需要的依赖。

   接着找出**项目工作目录**（如 `D:/mcp-tools/git-mcp-server`）和**实际启动入口**。`server.js`、`main.py` 在原笔记中是帮助理解的常见文件名，不能不看仓库就假设它们存在。后面配置中的 `cwd` 与启动参数，要与实际项目相符。

### 3.3 在 Cline 中写入并检查配置

原课程展示的入口是 Cline 侧边栏的 **MCP Servers → Configure → Configure MCP Servers**。截图能帮助找到当时的按钮；界面随 Cline 版本可能变化。当前 Cline 文档也描述从扩展内打开它实际使用的 MCP 设置文件，并在 `mcpServers` 下添加条目。

<img src="图片附件/Pasted%20image%2020260725140727.png" alt="课程截图中的 Cline MCP Servers 配置入口" width="257">

下面这张截图显示空配置的基本外层：

![空的 mcpServers 配置结构](图片附件/Pasted%20image%2020260725134324.png)

原笔记另写到，在项目根目录手动建立 `.cline/cline_mcp_settings.json`。这一做法没有从所核查的当前 Cline 扩展文档中得到通用项目级配置位置的确认；因此实际操作应优先打开 **Cline 自己正在使用的设置文件**，不要只因项目里存在同名文件就认为它会被读取。

对文件服务器，原课程截图展示的是 `mcpServers` **里面的一个服务器条目**，不是可单独粘贴的完整 JSON 文件。它用 `command` 指定启动命令，用 `args` 依次传入 `-y`、包名和允许访问的目录。`disabled: false` 表示条目未禁用，`autoApprove: []` 是 Cline 的自动批准设置；两者是客户端配置字段，不是 MCP 协议要求每个服务器都写的字段。

![文件服务器配置条目截图](图片附件/Pasted%20image%2020260725140548.png)

将上面的条目放入外层对象后，结构可读作：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "D:/code/work"],
      "disabled": false,
      "autoApprove": []
    }
  }
}
```

这份 JSON 是把原图中的条目和外层结构放到一起便于阅读，并非已在当前机器执行成功的记录。Windows 上若客户端启动 `npx` 失败，可以按该服务器或客户端说明尝试 `cmd /c` 包装：把 `command` 改成 `cmd`，并把 `args` 开头改为 `"/c", "npx"`，后面保留原来的 `-y`、包名和目录。不能只把 `npx` 改成 `cmd`、只加 `"/c"` 而漏掉要运行的 `npx`。官方服务器仓库给出了这一 Windows 示例；是否需要它仍取决于当前环境。

从源码运行的示例则要指向本机项目和它真实的启动脚本。课程截图的 `node`、`./server.js`、`cwd` 展示了这三个信息如何配合：**用什么运行、运行哪个文件、从哪个目录运行**。截图仍只是一个条目片段；不能保证任意克隆的仓库都有 `./server.js`。若某个 Windows 客户端无法直接找到启动命令，也应先查该客户端和对应运行时的说明，再决定是否包装命令，而不是机械套用上面的 `npx` 改法。

![源码服务器的 node、脚本与 cwd 配置条目截图](图片附件/Pasted%20image%2020260725142426.png)

配置后，原课程的检查顺序是保存 JSON（`Ctrl+S`），必要时通过命令面板查找 **Cline: Reload MCP Tools** 或重开 VS Code，再回到 MCP Servers 列表查看状态。状态标识只说明客户端当时的连接情况；还应确认工具确实出现在列表中，并在得到授权后尝试一次适当的工具调用，才能知道从配置到执行是否通畅。

### 3.4 把同一个 Server 配到 Cursor

原笔记接着问：已在 Cline 安装的 MCP Server，怎样给 Cursor 使用？其核心思路是**复用同一服务器的启动信息**，而不是“复制一次后所有客户端自然同步”。Cursor 当前文档确认项目级配置文件为项目根目录下的 `.cursor/mcp.json`，也提供用户级配置位置。

按课程的顺序，可以在项目里建立 `.cursor` 文件夹和 `mcp.json`，把所需服务器的命令、参数和环境设置作为起点写入 `mcpServers`，保存后让 Cursor 加载配置。原文说将 Cline 整份配置“原封不动”粘贴；实际迁移时应逐项核对 Cursor 支持的字段、目录路径、凭据及权限。像 `disabled`、`autoApprove`、`cwd` 等字段属于客户端实现，不能仅因 JSON 长得相似就保证行为一致。

课程还以黑色终端窗口和绿色状态灯判断是否启动。某些本地进程可能出现终端窗口，但这不是 MCP 协议要求，也不保证在所有 Cursor 版本中出现；关闭承载服务器进程的窗口可能使该连接中断。最终仍应在 Cursor 的 MCP 列表中检查服务器和工具，并通过实际工具调用验证，而不是只看颜色。

## 4. 从配置到调用：工具是怎样被模型用上的？

### 4.1 “配置了服务器”不等于“模型已经知道所有工具”

原笔记把这一过程分成“获取 MCP 列表”和“传给大模型”两步，这个提问方向很重要。不过 `mcp.json` 或 Cline 的设置文件主要记录**服务器的连接或启动信息**；不能假定它已经包含服务器所有工具的名称、说明和参数。客户端与服务器建立连接、完成初始化后，会用 `tools/list` 获取实际工具定义；之后宿主应用再决定怎样向模型呈现可用工具。

所以在前面的文件服务器例子里，配置里的目录是“这个服务器被允许处理哪里”的启动参数；服务器实际提供哪些工具，则要等连接并查询后才知道。图中的 JSON-RPC `tools/call` 是客户端调用服务器工具的一段协议消息，不是让模型直接读写本地文件。

### 4.2 工具清单怎样交给模型？

原笔记用比较表区分“写成提示词”和“按模型 API 的工具调用格式包装”，这有助于理解：**MCP 负责客户端与服务器之间的连接；模型看到工具的形式由宿主应用与模型接口决定。** 原表还把“MCP SDK 原生集成”列为第三种并列方式。SDK 可以帮助开发者实现 MCP 连接，但它不能代替宿主把可用工具提供给模型，也不是模型绕过提示词或工具接口直接与 Server 对话的独立通道。

| 原笔记比较的角度 | 把工具说明写入提示词 | 使用模型 API 提供的工具调用接口 | MCP SDK 在哪一层 |
| --- | --- | --- | --- |
| 基本做法 | 宿主把工具名称、用途、参数说明组织成模型可读的文字，并约定如何识别调用意图。 | 宿主把 MCP 工具定义转换为该模型 API 接受的工具定义；模型返回相应工具调用事件。 | 帮助程序连接 MCP Server、收发协议消息、实现客户端或服务器；与前两列可以同时使用。 |
| 对模型及接口的要求 | 需要模型能按说明表达调用意图，宿主还要可靠地解析。 | 需要所用模型 API 提供相应工具能力，具体格式随 API 变化。 | 主要是应用开发层的选择，不是额外的模型能力。 |
| Token 与实现代价 | 工具说明会占用上下文；实际用量受工具数、描述长度和对话策略影响。 | 结构化定义同样可能计入输入或工具开销；不能笼统断定一定比提示词省 Token。 | SDK 可减少协议实现工作，但不能据此推断模型 Token 消耗“极低”。 |
| 取舍 | 灵活，但说明和解析约定要清楚。 | 调用结构较明确，但需要适配具体模型 API。 | 省去手写部分协议代码，仍要处理宿主编排、权限与模型对接。 |

原表把 Cline、Claude Code、5ire、Codex 等产品放进某一固定列，还给出“最主流”和 Token 高低排序；由于这些实现会随版本变化，且原文没有测量条件，这里保留**比较维度**，不把产品归类或 Token 排名当成通用事实。

模型在看到用户任务和可用工具说明后，可能提出调用某工具的意图；并非一定是简单地做一次“语义相似度匹配”，也不一定直接输出一段可执行的原始 JSON。宿主解析模型返回的调用信息，再通过 MCP Client 向相应 Server 发出 `tools/call`，将结果送回模型或展示给用户。

### 4.3 “查上海天气，晴天写‘好’到桌面”：走完整条数据流

原笔记提出的任务有**两段**：先查天气，再依据天气决定是否写文件。原来的 11 步表把天气查询及回复讲清楚了，却在得到天气后直接进入最终回答，没有展开“如果晴天，再写文件”。下表的 13 步是依据原始 11 步数据流重新划分，并补入完成原始任务所需的**概念性后续分支**；它不是原课程逐项给出的 13 步执行记录。用户到模型、Server 再回模型的推导仍来自原笔记；条件判断和文件写入步骤也不代表课程或本笔记实际运行过。

| 步骤 | 谁在做 | 信息怎样流转 |
| --- | --- | --- |
| ① 用户提出任务 | 用户 → Agent | “查上海天气，如果是晴天写个‘好’字到桌面”。用户描述的是目标，不需要知道天气 API 和文件 API 的调用格式。 |
| ② 找到服务器 | Agent 中负责配置与连接的部分 | 读取客户端配置，知道应连接哪些 Server；此时得到的是启动或连接信息。 |
| ③ 获得工具说明 | MCP Client ↔ Server | 建立连接并请求工具列表，得到工具名称、用途和参数要求。 |
| ④ 组织模型输入 | Agent 中负责上下文构建的部分 | 把用户目标和可用工具信息按当前模型接口的形式组织起来：可能是说明文字，也可能是模型 API 的工具定义。 |
| ⑤ 请求模型判断 | Agent → 大模型 | 通过模型 API 发送请求。模型首先提出调用天气工具，例如 `get_weather`，并给出“上海”等参数。 |
| ⑥ 解析调用意图 | Agent | 识别模型要求调用的工具和参数，按客户端的授权与校验规则处理。 |
| ⑦ 调用天气工具 | MCP Client → 天气 Server | 将工具名与参数放入 MCP 的 JSON-RPC `tools/call` 请求；Server 可以再访问天气 API。 |
| ⑧ 返回天气结果 | 天气 Server → MCP Client → Agent | Server 返回工具结果，Agent 获得天气数据。数据具体格式由该工具决定，不能预设每个天气工具都返回同一种 JSON。 |
| ⑨ 让模型继续处理 | Agent → 大模型 | 将天气结果放入后续模型输入，让模型判断是否满足“晴天”条件。到这里，原课程表中的查询与结果回传主线已覆盖。 |
| ⑩ 条件不成立 | 模型与 Agent | 若结果不是晴天，应说明没有写文件；不应跳过条件直接调用文件工具。**这是为完成原用户请求补上的概念分支。** |
| ⑪ 条件成立 | 模型与 Agent | 若结果是晴天，并且文件服务器已连接、桌面目录在授权范围内，模型才可提出写入“好”的第二次工具调用；Agent 按客户端的授权规则执行。**这是概念分支，不代表已实际写入文件。** |
| ⑫ 执行写入并回传 | MCP Client ↔ 文件 Server | 客户端再发送一次 `tools/call`；文件 Server 返回成功或失败的结果。 |
| ⑬ 给用户答复 | Agent、模型 → 用户 | 根据真实工具结果说明天气与文件是否写入；不能只凭模型计划就说“已完成”。 |

这样回看原笔记的 11 步，模型像负责判断下一步的“大脑”，Server 接住对外部世界的具体操作，而 Agent／宿主应用负责**连接、转发、解析、授权和继续编排**。模型的调用意图与工具真正执行成功，是两件事。

### 4.4 把 Agent 内部职责拆开看

原笔记用四个组件解释“谁做什么”，很适合梳理刚才的数据流。这里把它看作**教学上的职责划分**，不是每个客户端源码里都必须有四个同名模块。

| 职责 | 在天气案例里负责什么 | 回答的问题 |
| --- | --- | --- |
| 配置加载器与 MCP Client | 读取服务器连接信息，与服务器建立连接，获得其工具列表，并发送后续 MCP 请求。 | “客户端怎么知道有哪些 Server 和工具？” |
| 上下文构建器 | 把用户任务、已有结果和工具说明组织成当前模型 API 接受的内容。 | “怎样把工具介绍给模型？” |
| 模型 API 接口 | 将整理后的输入发给模型，并接收文字或工具调用意图。 | “用户任务和工具定义怎么到模型那里？” |
| 响应解析与调度 | 区分直接回答与工具调用，选择对应 Server，处理结果后决定继续调用或结束。 | “模型要求调用工具以后，谁真正执行？” |

课程里“秘书处包装材料、给模型打电话”的类比，可以帮助理解第二、第三项之间的交接；真正的产品还要考虑客户端的权限和具体界面，但那属于实现选择，不改变这里的主线。

## 5. 我对 MCP 的阶段性理解

这份学习记录中最关键的认识是：MCP 把**应用与外部能力之间**的一段连接标准化了。工具定义不必一直由开发者硬写在模型提示词或适配代码里；客户端可以向服务器获取工具说明，再按宿主和模型 API 的方式呈现给模型。MCP 并没有规定所有模型都必须使用同一种原生 Function Call 机制，也没有替宿主做完任务判断与权限管理。

所以“模型会选工具”和“工具被安全、正确地执行”要分开看：模型提出下一步意图，客户端负责连接和调度，Server 执行它暴露的能力并返回结果。课程中的天气任务尤其说明这一点——查到天气只是中途一步，是否写文件、是否真的写成，都要看后续条件、授权和工具结果。
