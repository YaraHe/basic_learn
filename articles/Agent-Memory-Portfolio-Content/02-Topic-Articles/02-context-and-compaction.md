# 上下文如何保持可用：记忆工程、摘要与压缩

这篇文章整理自 DeepLearning.AI 的 *Agent Memory: Building Memory-Aware Agents* 课程学习笔记。截图和 32 条消息测试是课程示例，不代表我的项目实测。[^course]

对话越长，旧消息、工具结果和新问题就越可能挤在一起。本文要回答的是：**当前模型调用该带哪些信息？内容放不下时，怎样缩短输入而又保留找回细节的可能？**

## 先分清“存了什么”和“这次给模型什么”

模型处理的是**本次调用收到的上下文**，不是系统能够访问的全部数据库。上下文工程负责从系统指令、当前问题、历史消息、工具说明和检索资料中挑选本轮需要的内容，再组织成模型输入。窗口有限，塞进过多过时或无关信息，既占空间，也可能干扰当前判断。

![上下文工程：从多种来源选择本次输入](图片附件/Pasted%20image%2020260803120313.png)

记忆工程看的是更长的过程：哪些信息值得留下，怎样提取、标注、存储、更新，以及下次如何找回。两者接在一起才有用：**资料保存了却找不到，或找到了却没有进入本轮上下文，都不能帮助这次回答**。这是我理解两者关系的一种方式，不要求所有系统都采用同样的组件划分。

![记忆工程：记忆的生命周期](图片附件/Pasted%20image%2020260803143715.png)

课程还展示了记忆感知 Agent 的一种组织方法：在指令中说明可用记忆，把受控的读写能力注册为工具，再由应用规则或 Agent 的任务判断决定何时调用。模型可以**请求**读取或写入，实际执行和权限检查仍在外部程序中。这里的图是课程实现思路，不是 Agent 的统一架构。

## 摘要与压缩各解决哪一部分问题

当长对话接近窗口限制时，可以先生成一份较短的**摘要**，保留继续任务所需的事实、约束、已经做过的事、结果和未解决问题。摘要节省阅读篇幅，但会丢细节；尤其是数字、对象、否定条件和开放问题，不能只凭摘要就认定原意完整。

课程进一步演示了一种 **Context Compaction／offloading**：原始消息仍保存在外部存储；当前上下文改放较短的摘要和标识。若后续任务需要具体细节，Agent 可以按标识调用展开工具，取回与该摘要关联的原始消息。缩短的是**这一次交给模型的内容**，不是把存储中的原文压没了。其他平台也使用“compaction”一词，但具体保存形式和展开机制可能不同；这里讲的是课程代码路径。

这就带来一个取舍：摘要越短，当前输入越省；若保留的信息不足，Agent 就必须知道何时回查原文，而且原文与摘要的关联不能断。**保存了原文，也不代表模型会自动看见它。**

## 课程代码如何让短摘要还能回到原文

把分散的函数按数据流而非编写顺序来看，关键有五步：

1. **选出待处理消息。**课程按当前 `thread_id` 查询尚未摘要的对话记录，同时保留每条消息的 ID。这样才能知道本次摘要覆盖了哪些原文，而不是只留下一段没有出处的短文本。
2. **生成可继续任务的摘要。**课程提示词要求保留技术细节、情绪背景、实体与引用、行动项和决策，并区分已确认事实与开放问题。输出篇幅受限，但短并不等于可靠，仍需要检查关键条件有没有漏掉。

![课程摘要提示词：关注继续任务所需的细节](图片附件/Pasted%20image%2020260810112205.png)

3. **处理空输出，再写入关联。**课程在首次摘要失败或为空时尝试备用提示词；若仍得不到摘要，截图还显示用原文片段作兜底，并将缺失栏目标为不可用。这能避免把“没有生成”悄悄当成成功摘要，却不能保证兜底文本足够代表原对话。生成结果被赋予摘要 ID 并写入存储；参与处理的消息标记为已摘要，供下次筛选时避开重复处理。

![摘要失败后的重试与兜底处理](图片附件/Pasted%20image%2020260810154237.png)

4. **缩短当前上下文，保留展开入口。**课程用摘要引用替换本轮输入里的长段对话，同时保留存储中的原文。`expand_summary` 接收摘要 ID，读取摘要及其覆盖的原始消息，再把细节返回。它不是让模型根据几句话“猜回”逐字原文。

![按摘要 ID 读取摘要和原始消息的展开工具](图片附件/Pasted%20image%2020260810154717.png)

课程还把摘要操作注册到 Toolbox，允许在规定的调用范围内使用。**工具名与参数是这套代码的接口**；核心关系是“当前上下文中的短引用 → 外部存储中的摘要和原始消息”。

![课程中的摘要工具与登记方式](图片附件/Pasted%20image%2020260810161946.png)

5. **监测何时需要处理。**示例用字符数除以 4 粗估 Token，并设置 `256,000` 的窗口上限及 `80%` 的触发线。图中还按占用比例给出正常、警告、严重状态。这些是课程的演示参数，不是所有模型或产品的安全阈值；“约 4 个英文字符对应 1 Token”对中文、代码和工具定义可能不准，关键调用要按实际模型计数或留足余量。

![课程中的上下文占用监测与状态阈值](图片附件/Pasted%20image%2020260810162600.png)

### 用 32 条消息验证哪些环节

课程用一个研究计划对话作为测试线程，共 **32 条消息**。即使未达到自动阈值，仍手动运行摘要，以便观察写入结果。输出给出了摘要和 ID，也显示 32 条消息被标记为已摘要。这个数字说明课程测试处理了这一批记录，不是摘要质量分数。

![课程测试：32 条消息得到摘要及 ID](图片附件/Pasted%20image%2020260810181641.png)

接着按 ID 展开，课程能从存储里取回摘要及关联的原始消息；数据库检查还显示该线程剩余未摘要消息为 0、已摘要行为 32。测试因此验证了**写入、标记和回查链路**，没有证明摘要一定没有遗漏信息，也没有证明任何任务中都能正确决定何时展开。

![课程测试：数据库核对已摘要与未摘要消息](图片附件/Pasted%20image%2020260810203311.png)

## 真正需要保住的是什么

压缩后要继续完成任务，至少要能回答三个问题：**当前摘要是否留下了目标和限制？需要原文时能否按 ID 找到正确记录？取回的细节是否又被放进下一轮上下文？** 如果其中任何一环失效，外部数据库里“还有原文”也不足以保证回答正确。课程测试解释了这条机制，但具体的摘要质量、调用成本和触发条件仍应在目标任务上验证。
