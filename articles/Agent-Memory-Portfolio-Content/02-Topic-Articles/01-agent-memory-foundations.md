# Agent Memory：记忆类型、形成机制与读写流程

这篇文章整理自 DeepLearning.AI 的 *Agent Memory: Building Memory-Aware Agents* 课程学习笔记；课程代码与截图是一种具体实现，文中的分析不代表真实产品实测。[^course]

本文围绕一个问题展开：任务跨过多轮甚至多次会话时，Agent 怎样保存、找回并使用有用信息？先区分“当前要用”和“以后还要用”，再看记忆内容、存储与读写如何配合。

## 为什么 Agent 需要记忆

先区分自动化工作流与 Agent。预设工作流通常把步骤和分支提前写好；Agent 则可以根据当前任务和执行结果，判断下一步是调用工具、继续查资料、请求用户补充信息，还是结束。二者并非互斥，差别在于哪些决策预先确定，哪些留到执行时作出。

如果每次调用 LLM 都只给它当前一句话，前一轮说过的目标、已经查到的事实和执行过的步骤就可能丢失。一次任务可能跨多轮对话，甚至跨会话。记忆系统要做的，是让有用的信息在需要时还能被找到，同时避免把所有历史资料一股脑塞进有限的上下文窗口。

## 先看要记多久，再看要记什么

课程图先按使用范围分短期与长期，再把长期记忆分为程序性、语义和情景三类。**短期／长期回答“信息需要跨多久被找回”，后三类回答“留下的是什么内容”**。图把语义缓存也列在短期一侧，便于讲授，但缓存复用旧结果与保存任务经历是两种不同目的；不必把图上的每个框都理解为所有 Agent 必备的一张数据表。

### 当前任务的工作记忆，与用于复用结果的缓存

**工作记忆**可以想成任务中的“草稿纸”：当前目标是什么、用户刚说了什么、哪些历史约束仍有效、工具返回了什么、下一步还需做什么。模型每次调用只能处理送进本次输入的那部分信息，因而上下文窗口是工作记忆发挥作用的地方；但应用也可以把会话状态存起来，下一轮再挑选需要的部分。**工作记忆不等于整个上下文窗口，也不等于模型会自动记住所有过去内容。**

图中的**语义缓存**解决另一个问题：新请求与已经处理过的请求足够相近时，能否安全地复用旧结果，少做一次生成或检索。相似并不保证适用，复用范围还要考虑用户权限、上下文差异和资料时效；跨用户共享尤其不能只看问题文字像不像。它是减少重复计算的策略，不等于已经形成关于用户或任务的长期记忆。

### 跨交互留存的三类内容

长期记忆关注之后仍有价值的信息，可以沿着三个问题理解：

| 类型 | 要记住什么 | 直观例子 |
| --- | --- | --- |
| 程序性记忆 | “如何做”：规则、工具使用方式、可复用的步骤 | 系统提示词、工具箱、曾经整理好的工作流 |
| 语义记忆 | “知道什么”：相对稳定的事实、知识、实体关系 | 知识库、用户偏好、项目的已确认信息 |
| 情景记忆 | “发生过什么”：带情境和先后顺序的经历 | 历史对话、带时间戳的事件或会话摘要 |

**程序性记忆**不一定只来自 Agent 自己的经验。预设的规则、代码和系统提示词也在规定“如何做”；课程还把可检索的工具说明和工作流记录放进这一类。一次流程的步骤与结果可以成为下次处理相似任务的参照，但不能因为保存了流程就说模型权重已被训练改变。提示词、外部工作流记录与模型参数是不同层面。

**语义记忆**包括事实和知识：知识库已有的资料，以及从交互中核对过的用户偏好、项目状态等。这里的“语义”指记住什么，**语义搜索**则指按含义查找，是一种读取手段。事实可以存成结构化字段或文本；资料也可以建立向量索引，实体关系还可以用图结构表达。课程举了向量库、知识图谱和 SQL 库等方式，但记忆类型与数据库类型并非一一绑定：例如固定的用户偏好可以直接按字段查询，不必先转成向量。需要从知识库找资料时，也可以取相关片段放入本轮上下文，这与 RAG 的“先找资料、再回答”相通。

**情景记忆**关注过去发生过的事：谁在什么情境下做了什么、经过哪些步骤、结果如何。课程把对话及其摘要放在这一类。可以保留原始消息，也可以留摘要或可检索的事件记录；摘要方便回顾，但可能丢失细节。时间戳有助于按时间找经历，却不是划分情景记忆的唯一标准；也可按当前问题与过去事件的相关性检索。

> 一个帮助我理解的比喻：工作记忆像**草稿纸**，供当前任务推理；过去经历可记进**日记本**，经核对的稳定事实可进**档案柜**，需要重复步骤时可翻**说明书**。这是一条可能的整理路线，并非每次交互都会依次经历四种记忆。

### 聊天记录何时成为长期记忆？

一段对话不会自动成为可靠的长期记忆。系统需要决定**何时提取、提取什么、怎样核对、写到哪里**。可选触发方式包括：会话结束后处理；上下文占用达到预设阈值时处理；识别到某种意图时处理；或通过定时任务处理。它们可以组合，不要求每种系统都用同一组触发器。

课程的一种做法是在会话结束后或上下文接近阈值时整理对话，为摘要附上时间和会话标识，并保留与原始消息的关联。这是**可选的记忆整合流程**，不意味着每次会话都必须异步运行一个小模型，或所有情景记录都要保存为“摘要”。课程示例中的 `user_id`、`timestamp`、`session_id`、`summary` 有助于按人、时间和会话查找；实际字段应由检索、权限与保留要求决定。

提取时，可以使用规则与实体识别，也可以让模型按提示词找出候选信息。要优先区分“用户确实确认的长期事实”“临时讨论的想法”和“尚未解决的问题”。例如“预算是 50 万”若只是讨论中的假设，就不能直接写成已确认状态。抽取后还要决定是否与已有记录冲突：较新的时间戳是一个线索，但不能无条件让新话覆盖旧话，还需看来源、确定性和业务含义。

课程示例把对话、摘要、知识、实体、工具和工作流分开组织，再按读取方式选择 SQL 表或向量检索结构。这些是**记录用途**与**访问方式**的区分，不等于六种内容必须分别采购数据库。有些数据库同时支持关系字段与向量搜索；是否采用一个存储系统，还要看权限、事务、一致性、检索能力和维护成本。

## 把记忆放进 Agent 系统

### 记忆在哪里：模型之外还需要什么

课程用八层图说明 Agent 不是只有一个 LLM。读这张图时，重点不是背下层名，而是看**谁让记忆进入本轮决策，谁负责保存，以及模型能否自行执行读写**。

![课程中的 Agent 系统栈](图片附件/Pasted%20image%2020260803111550.png)

| 课程图中的层次 | 与记忆有关的分工 |
| --- | --- |
| Application、Gateway and Connectivity | 接收请求、识别用户及其权限，并把回复呈现给用户。权限也影响哪些历史信息能被读取。 |
| Orchestration、Reasoning、Tooling | 应用组织当前上下文和执行步骤；LLM 基于提供的信息提出判断或工具请求；外部程序校验并执行读写。 |
| Data Layer、Governance and Reliability、Infrastructure | 数据层保存事实、事件和工作流；可靠性层关注访问、日志和故障；基础设施提供实际存储与计算。 |

这只是阅读课程图的分组，不要求实际产品逐层部署。它解释了为何“让模型记住”不能只靠提示词：历史需要有人存，当前任务需要有人找，读取还要受权限和运行规则约束。

课程图把不同记录及其读写方法放在 **Memory Manager** 周围。可以把它理解为 Agent 使用记忆时的一层接口：应用按需要请求读写，管理器再通过课程提供的存储能力处理相应记录。课程笔记还使用 **Memory Core** 和 **Storage Manager** 等名称；现有截图不足以把这些名称与具体类、数据库连接及管理器职责一一对应，不能凭名称推断其完整分工。


### 记忆操作由谁触发

图中把对话、知识库、工作流、工具箱、实体、摘要和 Persona 作为不同记录用途，并通过管理器提供对应的读写方法。例如需要回答用户偏好时，可能读取已核对的事实；需要复用流程时，则找工作流记录。图里的存储表及方法名是**课程代码安排**，不要求实际产品照搬七类表。

![课程示例中的记忆类型、存储与读写操作](图片附件/Pasted%20image%2020260803113833.png)

同样是读写记忆，触发者可以不同：

1. **规则触发：**程序按预设条件或时间执行，例如达到课程设定的上下文阈值后启动摘要。规则确定的是**何时调用**，不等于模型生成的摘要内容完全确定。
2. **Agent 触发：** 把部分记忆操作暴露为工具，由 Agent 在任务中判断何时检索或展开摘要。模型提出工具调用请求，真正的读写仍由外部程序执行；写入是否允许，也可以由应用规则控制。

![确定性操作与 Agent 触发操作](图片附件/Pasted%20image%2020260803115125.png)

一条被保存的**记忆单元**可理解为课程存储和检索的一条记录，而非所有数据库共同的“最小原子”。对话记录可能含角色、时间和内容；工作流记录可能含步骤、运行结果及用于检索的表示。字段随用途而变，不要求所有记忆具有同一模式。

![不同记忆单元的示意](图片附件/Pasted%20image%2020260803115741.png)

回到开头的问题：**保存**决定过去的什么能留下，**检索**决定这次找回什么，**上下文组织**决定模型实际看到什么，**更新与遗忘**决定未来还能否依赖它。记忆的价值不是把全部历史直接塞给模型，而是让任务需要的信息在合适的时机可用。
