# 工作流记忆与记忆感知 Agent 的执行循环

这篇文章整理自 DeepLearning.AI 的 *Agent Memory: Building Memory-Aware Agents* 课程学习笔记。文中的天气任务、代码和截图都是课程示例，用来理解系统如何协作，不代表我亲自完成或验证的产品项目。[^course]

Agent 的记忆可以保存对话、知识、执行步骤、实体和摘要；真正执行任务时，系统还要决定本轮取回哪些内容、提供哪些工具。这里进一步追问：**一次任务开始时，Agent 怎样取回有用的记忆；任务执行中，模型、工具和记忆怎样交换信息；任务结束后，哪些记录会留下来供以后使用？**工作流记忆是贯穿这条数据流的一个例子。

## 从天气任务看工作流记忆

如果只保存“今天的天气如何”这句最终回答，下次遇到类似任务时，系统仍不知道中间做过什么。课程中的天气示例依次获取用户位置、调用天气服务、传入经纬度、取得天气，再返回回答。这里值得记住的是**有序步骤**，以及每一步需要什么输入、产生什么输出。

<img src="图片附件/Pasted%20image%2020260806162747.png" width="382" alt="课程天气工作流的五个有序步骤">

一条工作流记录可以包含名称、可选描述、最初的请求、有序步骤，以及执行状态或结果。课程还列出 `run_id`、时间戳、JSON 流程文档、向量表示和 `thread_id` 等字段：有的帮助追踪一次运行，有的帮助以后检索相关记录。这是课程采用的记录方式，不意味着每个 Agent 都需要相同字段。旧工作流可以作为参考，但不能因为步骤曾经执行过，就假定下次环境和结果也相同。

## 循环前：取回记忆，准备上下文和工具

一次 Agent Loop 可以简要理解为：程序先组织消息并调用模型；模型回答，或提出工具请求；程序执行工具，把结果交回模型，再决定是否继续。模型不会自行在后台执行工具，这个调用与回填的循环由外部程序控制。 课程的简化例子设置了 `MAX_STEPS`，模型返回 `final` 就结束，返回 `tool` 就执行并继续；这两个行动名称是示例写法，并非所有实现的固定接口。

在进入循环**之前**，课程程序先读取会话记录、知识库、已有工作流、实体和摘要，再把它们按来源组织进本次上下文。系统提示词解释这些分区是什么、应怎样使用：如果关键细节只在摘要里，就按需展开；资料冲突时关注当前问题和较新的明确指令。提示词还限定使用本轮提供的工具，并要求在记忆不足时说明缺口。这些是课程示例的约定，不是通用的统一提示词。

![课程示例的系统提示词与记忆分区](图片附件/Pasted%20image%2020260812143559.png)

课程的 `call_agent` 接收用户问题和 `thread_id`，随后按顺序准备本轮输入：

1. **读取记忆。**通过课程提供的接口，按问题读取上述几类历史与知识，再整理成不同分区。记忆并非凭空出现在模型里，而是由程序从外部存储取回并放入消息。
2. **检查上下文占用。**估算整理后内容占用了多少窗口；超过课程设定的 `80%` 时，调用摘要或卸载流程并重新估算。代码保留当前用户问题，再处理较早的信息，避免把本轮需求一并压掉。`80%` 是这段课程代码的阈值，不是所有系统的规则。
3. **筛选工具。**Toolbox 按问题检索本轮相关工具；图中 `k=5` 也是示例参数。检索到的工具只是候选项，真正调用了哪些工具，要看后续循环中的请求和执行结果。
4. **记录本轮输入。**课程把用户消息写入对话记忆，也尝试提取实体，然后组合系统提示词、用户问题、记忆上下文与可用工具，交给模型开始判断。

![循环前：读取记忆与检查上下文占用](图片附件/Pasted%20image%2020260812145924.png)

![循环前：检索工具、保存用户消息和提取实体](图片附件/Pasted%20image%2020260812151017.png)

因此，循环前的数据流是：**按问题取回相关记忆 → 检查并必要时压缩上下文 → 选出可用工具 → 保存本轮输入 → 把材料交给模型。**读取和筛选发生在模型第一次决策之前，能减少它当场面对的历史内容和工具说明；但筛选不等于执行，也不能保证选出的内容一定相关。

## 循环中：工具执行、日志保存与结果回填

准备好消息后，程序进入有上限的循环。课程用 `call_openai_chat` 把消息和本轮工具定义交给模型；如果模型提出工具请求，外部的 `execute_tool` 再按工具名到 Toolbox 找到函数并执行。**模型负责提出请求，外部程序负责实际调用。**截图中的 `execute_tool` 还为特定摘要工具补入线程 ID，这是这套课程实现的细节，不能推成所有工具调用的统一流程。

![工具执行函数与模型调用函数](图片附件/Pasted%20image%2020260812144519.png)

执行后，课程把工具名、参数、完整结果、成功或失败状态及错误信息写入工具日志；供模型继续判断的结果则放回消息列表。截图中，较长结果在回填前会截短，而完整输出留在日志里。这样可以把**本次确实发生了什么**保存下来，同时控制下一轮送进模型的内容长度。日志和当前上下文承担不同作用：前者保留执行记录，后者只放模型继续回答所需的信息。

![课程中工具执行、错误处理与完整日志写入](图片附件/Pasted%20image%2020260812155845.png)

下一轮模型看见刚才的工具结果，再决定继续请求工具还是输出最终回答。课程为循环设置最大迭代次数；达到上限仍无最终答案时，会返回预设的未完成提示。这里能确认的是截图展示的工具调用、日志与回填路径，不能据此推断这套示例已经实现了课程材料未展示的权限管理或更完整的异常恢复机制。

下图把这些动作放回整体位置：左侧先读取记忆，中央反复组装上下文、让模型决策并执行行动；循环内也可以按需要检索或展开记忆；到达停止条件后，再处理本轮留下的记录。图中的 *harness* 指组织消息、调用模型、执行工具并控制循环的外部程序结构，不是一种新的记忆类型。

## 循环后：留下对话、步骤和可检索的记忆

循环结束时，课程尝试把本轮有序步骤保存为工作流，抽取实体，并把 Agent 的最终回复写入对话记忆。配合循环内已保存的工具日志，这些记录分别回答不同问题：**说过什么、调用过什么且结果如何、任务按什么顺序推进。**天气案例中的有序步骤，正是在这类运行之后才可能成为以后可查找的工作流记忆。

![工具结果回填、停止条件及循环后写入](图片附件/Pasted%20image%2020260812171742.png)

这也解释了为什么记忆操作分布在循环前、中、后：开始前取回有用信息，执行中按需要调用工具并留下真实结果，结束后才有本轮对话和步骤可供整理。某些读取或摘要由代码按固定条件触发，另一些要等模型在循环里提出请求；保存时机和记录内容需要按具体实现看，不能只用“Agent 有记忆”一句话概括。

## 关键取舍与仍待理解的问题

- **上下文不等于存储。**完整工具结果留在日志，给模型的回填可以较短；较早对话也可以摘要并留原文索引。减少上下文占用的同时，系统仍需要能找回关键细节。
- **取回和筛选要有边界。**循环前读取记忆与工具可减少当轮需要浏览的材料，但相关性仍可能判断不准。课程中的 `80%` 和 `k=5` 只能说明这套实现如何控制输入规模，不能直接当成产品选型结论。
- **过去的步骤是参考，不是下次执行的保证。**工作流保存了顺序、输入输出和结果；是否复用以及怎样复用，仍取决于新任务和当时环境。

原始学习记录还留下两个问题，需要结合课程缺失部分或完整代码继续核对：

1. **Storage Manager 与 Memory Manager 怎样分工？**现有截图能看到初始化、记忆读取和写入的调用顺序；但在“用户询问产品信息，需要查产品数据库”的具体场景里，Agent、LLM 与两个管理器如何逐步交接，材料还不足以给出确定的职责划分。
2. **Toolbox 的边界在哪里？**截图能说明工具注册、按问题检索以及按名称执行；工具如何存储、权限如何处理、与管理器之间有哪些完整接口，不能凭现有片段补成已实现事实。
