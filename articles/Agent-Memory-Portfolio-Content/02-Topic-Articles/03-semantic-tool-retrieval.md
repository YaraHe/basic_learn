# 工具太多怎么办：语义检索与工具调用

这篇文章整理自 DeepLearning.AI 的 *Agent Memory: Building Memory-Aware Agents* 课程学习笔记；

当可用工具变多，直接把全部工具交给模型会占用上下文。课程从工具调用的基本过程出发，比较原始说明检索与增强说明检索。

## 工具调用先是一次请求，再是一次执行

LLM 本身不会因为输出了“调用天气工具”几个字，就真的访问天气服务。在常见的函数调用流程中，应用先提供工具名称、说明和参数格式；模型返回结构化的工具调用请求；应用验证并执行；工具结果再交回模型，模型据此继续回答或调用其他工具。课程把工具说明及其用法看作一种程序性记忆。

![LLM 提出工具调用、外部程序执行并回传结果](图片附件/Pasted%20image%2020260806105723.png)

工具数量少时，把定义直接交给模型较容易管理；工具数量多时，名称、描述和参数会占据大量上下文，还可能让相似工具更难区分，并增加调用成本与延迟。这不是“工具越多，回答一定越好”，也不是“多于某个数量就必然失败”。

![工具数量增加时，上下文与选择都面临压力](图片附件/Pasted%20image%2020260806110420.png)

课程的办法是先筛选：**把工具当成可搜索资源，当前任务只给模型一小组相关工具**。例如用户问“伦敦明天天气如何”，优先找天气相关工具，不必同时展示计算器和翻译工具。此处的 Top-K 是候选数量，需要结合任务测试，不能固定取某个数字。

## 方案一：按原始工具说明进行语义检索

这套流程可以拆成离线准备与在线使用：

1. **离线准备：** 整理每个工具的名称、描述和参数，把描述编码成向量，与原始工具定义一起存入可检索的存储系统。
2. **接到问题：** 将用户问题编码，并与工具向量比较，找出语义最接近的少数候选。
3. **让模型选择：** 只把候选工具的完整调用定义交给 LLM，由它生成结构化请求；外部程序执行命中的工具，再把结果回传给模型。

![把工具定义建索引，提问时只召回相关工具](图片附件/Pasted%20image%2020260806110642.png)

这个方法把筛选工作从大段提示词挪到检索阶段，但也有明显边界：若原始工具说明短而含糊，两个用途相近的工具在检索时仍可能混淆。仅靠嵌入相似度也不能代替工具权限、参数验证或执行结果检查。

## 方案二：先增强工具说明，再建索引

课程接着提出 **Memory Unit Augmentation**。把工具原有的名称、描述和参数交给 LLM，生成更清楚的适用场景、边界和典型调用方式；然后用增强后的说明生成嵌入，存入工具库。这个增强发生在**建库阶段**，不是每次用户提问都重新扩写一遍。在线提问仍沿用“检索少数候选 → 模型选工具 → 外部执行”的流程。

![课程中的工具记忆单元增强流程](图片附件/Pasted%20image%2020260806111200.png)

这样做的意图是让工具描述携带更多可检索的信号，帮助区分相似工具。更高的召回率和区分度是课程提出的设计预期，具体是否改善召回与误选，要用实际工具集和问题验证。增强说明还须核对原始工具能力，避免模型写出工具并不支持的参数或用途。
