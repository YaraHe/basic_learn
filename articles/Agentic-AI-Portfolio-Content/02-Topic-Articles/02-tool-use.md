# Tool Use：从工具请求到代码执行


## 工具在工作流中扮演什么角色

工具是应用提供给模型使用的函数或外部能力。用户提出问题后，模型可以查看可用工具的描述，决定是否需要工具，以及调用哪一个；开发者则先根据应用目标实现相应的函数，并规定允许模型访问哪些能力。模型生成的是**调用请求**，真正执行函数的是应用程序或承载它的工具运行环境；执行结果再返回给模型，让它继续处理用户任务。

## 手写 `FUNCTION` 标记：理解工具循环的简单例子

课程先用查询当前时间的函数 `get_current_time()` 解释底层过程。这不是所有 Agent 系统必须采用的语法，而是为了看清每一环节的教学写法。

1. 开发者先实现能返回当前时间的函数。
2. 在系统提示中告诉 LLM 有这个工具，并约定当它需要调用时输出 `FUNCTION get_current_time()` 这样的文本。
3. 用户问当前时间，模型按约定输出该标记。此时模型**尚未真正调用**函数。
4. 应用代码检测输出中的 `FUNCTION` 标记，实际执行 `get_current_time()`。
5. 函数返回时间；应用程序把工具调用事实和结果，连同必要的对话上下文，重新送给模型。
6. 模型依据结果继续生成回答，必要时还可再次请求工具。

![课程图：手写函数调用标记与执行流程](图片附件/Pasted%20image%2020260815170550.png)

因此，“让 LLM 使用工具”至少包含四件事：实现并描述工具、让模型发出特定格式的请求、由程序执行、把结果反馈给模型。课程把这种手写大写 `FUNCTION` 文本的方式称为 *all-caps function syntax*。支持原生工具调用的模型接口可以输出结构化工具请求，不需要依赖这个教学用字符串约定；但模型请求与程序执行的分工仍然成立。

那另外一种常见的办法则是原生工具调用，用JSON Schema声明工具模型，返回结构化的tool calls，程序执行后回传结果。如下面案例所示。

## 课程中的 AI Suite 示例：描述生成与执行循环

课程随后使用开源包 AI Suite 展示更方便的封装。第一张图左侧定义 `get_current_time`：函数体返回时间，文档字符串说明用途；右侧用 `client.chat.completions.create(...)` 调用模型，把该函数放进 `tools=[get_current_time]`，并设置 `max_turns=5`。模型据此获得工具描述，才有机会判断何时请求它。

![课程图：AI Suite 接收 Python 函数作为工具](图片附件/Pasted%20image%2020260815222710.png)

在这个课程示例中，AI Suite 从【函数名、文档字符串和参数信息即上图左部分代码】生成提供给模型的工具描述。图中的无参数函数会形成较简单的 JSON Schema；增加 `timezone` 参数后，描述还需要包含参数名、类型及用途。文档字符串不是函数执行结果，而是帮助模型理解“这个工具能做什么、何时用”的材料。

## CodeAct-让模型编写代码：能力更灵活，执行也要受控

如果任务所需操作很多，一个个预先实现工具未必方便。课程提出另一种方式：不需要让模型一个一个选工具，而是让模型直接写代码，在沙箱里调用函数，一步解决多步逻辑。下图中展示了这一思路。

![课程图：通过代码执行完成任务](图片附件/Pasted%20image%2020260817123819.png)

课程图中用“求 2 的平方根”说明完整流程：模型输出带 `<execute_python>` 标记的 Python 代码，执行程序运行代码并取得数值，再把结果送回模型，由模型组织自然语言答案。

如果走传统的工具调用，用户要算平方根得先写sqrt工具，要算方差得先写variance工具，工具越堆越多。
让模型写代码，相当于给它一整个Python生态。那代码串起读文件、算数据等多个步骤，无需提前把每个动作都分装好。

课程也提到可用 Python `exec` 执行代码，或考虑 Docker、E2B 等隔离环境。它们是不同的执行安排：仅调用 `exec(output)` 并不等于已经隔离了代码；即使使用沙盒，也仍需按任务限制可访问的文件、网络与权限。 这里的重点是**模型生成代码和程序执行代码是两件事**，不能把“模型会写”直接等同于“可以无条件运行”。
