# Agentic AI 评估：从基线到错误分析与优化

## 从一个能运行的基线开始

开发 AI 系统时，很难只凭设计预先判断哪些步骤会有效。课程建议先做一个简单、能运行的版本，观察结果，再有针对性地改进。这个建议也与反思的思路相通：先得到实际输出，才能知道问题发生在哪里。下面通过几个案例来理解eval。

## 发票到期日提取：把“看起来不错”变成可测量的问题

课程案例是发票处理工作流：先把 PDF 转成文本，再由 LLM 提取开票方、地址、应付金额、到期日等字段，最后更新数据库。图中的某些发票会把**发票日期**与**到期日期**弄混。*只看一次成功输出，无法知道这个错误有多常见，也无法判断一次提示词修改是否真有帮助。*

![课程图：发票字段提取与到期日错误](图片附件/Pasted%20image%2020260817153231.png)

在这种情况下,可以考虑的是
(1)如何改进系统,以便更好的提取到期日期
(2)为了跟踪优化进展,也可以编写一个评测,用来衡量系统提取到期日期的准确率

围绕到期日，原笔记记录了一套具体评测流程：

1. 收集课程示例所说的约 10～20 份发票，逐份人工标出正确的到期日，作为测试集的参考答案。这个数量用于**快速起步**，不是所有应用的固定样本量。
2. 把参考日期统一写成同一种格式；提示模型也按相同的“年/月/日”格式输出，避免“日期其实相同，只是写法不同”干扰比较。
3. 写一段代码，从模型的完整输出中提取到期日字段。
4. 逐份比较提取结果与人工标注是否一致，统计正确比例。
5. 调整提示词或流程中的其他部分，比如说换提示词、加反思步骤、换算法、换模型等，都用同一批数据测试，观察正确比例是否提升，并查看仍然出错的发票。


![课程图：从简单原型开始并逐步评估](图片附件/Pasted%20image%2020260817150044.png)


## 评估有两个常用维度

课程图中的“两条轴”分别是：**用代码作客观判断，还是请 LLM 按标准作主观判断**；以及**每个样例有没有已知的参考答案**。例如，发票到期日有人工标注的正确日期，可用代码比对；营销文案长度即使没有逐样例标准答案，也能用长度规则检查。若为每个样例准备了必须覆盖的要点，可让 LLM 判断输出覆盖了几个；评价图表时即使没有单一“标准图”，也可先确定好的图表有哪些标准？然后让 LLM 按确定的标题、坐标轴等标准打分，这比笼统的问”哪张图好”更好。。
在总结选评估方式的顺序是：
1. 先看任务能不能写成确定的规则。
2. 再看有没有参考答案。
能写成规则，则用代码；稳定、便宜。不能才让LLM当裁判，并且要给他明确的评分标准。

![课程图：客观或主观评估，以及是否有逐样例参考答案](图片附件/Pasted%20image%2020260817155645.png)

另一个与图中两条轴不同的问题是**评估范围**：看整条流程的最终结果，还是看某个中间组件。后面的错误分析和网页搜索案例会继续解释两者的关系。

评估方法本身也要迭代。起初可以用几十个样例、简明代码规则或评审提示快速找到问题；随着案例积累，再完善数据和标准，减少每次修改提示词都只能靠人工通读大量结果的负担。尤其当某个指标与人的判断不一致时，要改进评测标准，并查找系统表现明显不如人处理的案例。

![课程图：从简易评测起步并修正不贴近人工判断的指标](图片附件/Pasted%20image%2020260817160611.png)

## 错误分析：先定位问题，再决定优化哪里

端到端分数只告诉我们最终效果，不一定告诉我们原因。课程的研究 Agent 示例把流程展开为：用户提问 → 模型提出搜索词 → 网页搜索 → 模型筛选五个较好的来源 → 抓取网页内容 → 模型写文章草稿。最后的文章如果不好，可能是搜索词不对、搜索结果质量低、来源筛选不佳，或模型阅读材料后推理和写作出了问题。

![课程图：研究 Agent 的流程与潜在错误位置](图片附件/Pasted%20image%2020260817202624.png)

要分清原因，就检查运行记录中的中间步骤及其输入输出，并与人在相同输入下会做出的较好结果比较。记录整个运行过程通常称为 *trace*；其中某次操作可作为一个 *span*，它可以记录该步的输入、输出、耗时等信息，不能把 span 简单等同于“单步输出”。

接着收集失败案例，给每个案例标出明显不足的环节。例如某任务的搜索词太泛，另一个任务的搜索结果混入过多不合适的网页，再一个任务遗漏了关键来源。图中的表格按步骤累计这些错误，示例里搜索结果栏的错误比例明显高于搜索词栏，于是下一步更值得先检查搜索质量，而不是平均投入所有组件。但比例来自图中的示意案例，不是对真实系统的普遍统计；还要结合错误的严重程度和修复成本作判断。

![课程图：逐案例记录错误出现在哪个步骤](图片附件/Pasted%20image%2020260817204100.png)

因此，错误分析的作用是把“系统表现不好”变成“哪个步骤、在哪类输入下、以什么方式表现不好”，为下一轮优化排序。

![课程图：错误分析帮助确定下一步](图片附件/Pasted%20image%2020260817204345.png)

## 组件评估与端到端评估相互配合

如果错误分析指出网页搜索质量需要改进，每次都重跑整条研究 Agent 流程会比较昂贵；下游模型本身的波动也会掩盖搜索结果的小幅改善。可以单独评估网页搜索组件：准备若干问题及值得找到的参考网页，比较搜索结果命中这些网页的情况，再调整搜索引擎、返回条数、日期范围等参数，看指标有没有变好。课程图中举了类似 F1-score 的衡量方式；具体指标仍要与搜索任务目标相符。

注： F1-score是一个综合指标，用来搜索搜出来的东西有多少是对的，同时该找到的东西有没有漏掉，它是由精确率和召回率调和平均得到的。

![课程图：单独评估研究 Agent 中的网页搜索](图片附件/Pasted%20image%2020260818100908.png)

组件级评估能帮助快速判断“这一环节是否变好了”，却不能单独证明最终文章也一定变好。调整组件后，仍需做一次端到端评估，确认新的搜索结果确实改善了整条工作流。反过来，如果整体结果不佳，又可回到中间步骤继续定位。

## 找到问题后，选与问题相称的改法

**非 LLM 组件**（网页搜索、RAG 检索、代码执行、语音识别等）可以先调整自身参数。例如搜索结果数量和日期范围、检索相似度阈值和分块大小、检测阈值；如果仍不合适，再考虑替换搜索引擎、检索服务或其他组件。课程图示的是一组可能的手段，不是说每种组件都能用同一种参数解决问题。

![课程图：改善非 LLM 组件的两类办法](图片附件/Pasted%20image%2020260818101833.png)

**LLM 组件**可先检查指令是否清楚、是否缺少具体示例；还可以比较不同模型，用同一评测集选择适合当前任务的模型。如果一个步骤要求模型同时完成太多复杂指令，可以尝试把它拆成更小的两三步，再测整体效果。课程也列出在合适数据条件下微调模型这一选项。拆分步骤可能提高准确性，也会改变延迟和成本，因此仍须评估。

![课程图：改善 LLM 组件的几种办法](图片附件/Pasted%20image%2020260818102527.png)

模型选择的直觉可以通过经常试用模型、保留个人常用评测题，以及阅读他人的提示词来培养。不同任务可能适合不同模型；课程截图还提到用 AI Suite 较快地切换模型做对比。这是探索方法，不等于已经得到某个模型在所有任务上的排名。

![课程图：通过试用和评测形成模型选择直觉](图片附件/Pasted%20image%2020260818103247.png)

## 质量之外，还要看延迟与成本

工作流效果可用之后，实际使用还会受到速度和费用影响。先记录每个步骤耗时，再看完整时间线：课程图的研究 Agent 中，搜索、抓取、模型生成各花不同时间。若几个步骤互不依赖，可考虑并行；若某次 LLM 调用占用时间很长，可试更快的模型或服务商。但速度改进不能只靠猜测，也不能牺牲必须的质量检查。

![课程图：按步骤记录研究 Agent 的运行时间](图片附件/Pasted%20image%2020260818105004.png)

同理，可以估算各步骤费用：模型调用可能按 token 或 API 调用计费，其他计算步骤还与服务及资源使用方式有关。

![课程图：按步骤估算研究 Agent 的费用](图片附件/Pasted%20image%2020260818105851.png)

总结：先让系统能完成任务，再用输出与运行记录、评估指标和错误分析找改进点；改进组件后，回到整体结果继续验证。课程总结图把“构建”和“分析”画成双向循环，而非做完一次就结束。当工作流逐渐可用，再沿时间与成本两条线找优化空间。
