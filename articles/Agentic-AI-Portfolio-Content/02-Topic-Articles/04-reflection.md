# Reflection：反馈驱动的自我修正与效果评估

本篇通过SQL修正、代码调试等具体案例，阐述在AI Agent开发中引入“reflection"机制时的底层设计思想与评估逻辑。

## 反思从哪里得到反馈

模型可以审查自己刚生成的内容，也可以由另一个模型扮演评审者。另一类反馈来自工作流外部：例如运行代码后的报错信息，能够让模型知道“哪里真的没有运行成功”。于是流程从“生成一次就结束”变成“生成 → 审查或获得反馈 → 修改”。反思**可能**提高质量，但是否有效，需要评估而不是预设。

## 写反思提示时，要说清审查动作和标准

提示词可以给出期望的输入输出示例。没有示例叫零样本；一个示例可称单样本；多个示例通常称少样本。**示例数量与是否运行反思是两个不同维度**：零样本提示也可以要求模型先生成、再审查；给了示例也不保证一定发生反思。

![课程图：反思提示示例](图片附件/Pasted%20image%2020260815115843.png)

除了示例，还应明确告诉模型要做什么审查动作，例如“review”，以及按什么标准或步骤检查。课程的图表示例是：第一个 LLM 生成绘图代码；第二个 LLM 接收初版代码、生成的图表与对话背景，检查可读性、清晰度和完整性，再提出改进并写出新版代码。这里的关键不是“再调用一次模型”本身，而是**第二次调用有明确的审查任务和可参考的材料与标准。**

![课程图：模型生成图表后进行反思](图片附件/Pasted%20image%2020260815152321.png)

## 怎么判断反思真的带来了改进

课程把反思效果的评估分成两类：有客观答案的任务，以及需要主观判断质量的任务。

![课程图：反思工作流的评估方式](图片附件/Pasted%20image%2020260815150719.png)

**一个问题有客观答案时，比较使用反思前后的正确与否。** 
例如模型生成 SQL Query，执行得到结果。
再让同一个或另一个模型反思并改写刚才的SQL Query，得到V2 SQL Query,然后执行；
将两者结果与客观答案比较，哪个版本的SQL Query执行获得的结果更正确或者说正确的更多。

![课程图：SQL 查询的反思案例](图片附件/Pasted%20image%2020260815143423.png)


**多个问题有客观答案时，比较使用反思前后，哪种正确率更高**
可以收集一组用户问题及对应的标准答案，分别运行“不反思”和“加入反思”两种流程，比较各自答对的比例。课程表格以 87% 与 95% 展示一次示例对照；这一方法也适用于在多个备选提示词之间做出选择。

![课程图：以标准答案比较反思前后](图片附件/Pasted%20image%2020260815143805.png)



**没有唯一标准答案时，需要主观标准判断“更好”。** 例如让模型制作图表，反思前后的作品在表达上哪一个更清楚，这种情况难以只靠字符串相等判断。课程演示了让另一个 LLM 比较两份输出。
但直接问“哪份更好”也会有局限：
- 模型的偏好不一定与人的判断相同，
- 答案摆放顺序也可能影响评判。
![课程图：主观任务中的成对比较](图片附件/Pasted%20image%2020260815144541.png)



因此，课程进一步给出一个更具体的办法：预先定义若干检查项，让评审模型对每项给出 0/1 判断，再汇总分数，并用多组反思前后的输出比较效果。截图列出“标题是否清楚、坐标轴标签是否齐全、图表类型是否合适、数值范围是否恰当”等比较项；
相较笼统地打 1～5 分，这个做法让评审依据更明确，但不应推断二元评分在所有任务上都更准确；仍要检查标准本身是否贴合任务、评审结果是否可靠。

![课程图：为主观评审设置多个二元标准](图片附件/Pasted%20image%2020260815145250.png)

![课程图：汇总评审结果以比较反思效果](图片附件/Pasted%20image%2020260815145733.png)

如果改了最初的生成提示词，或改了反思提示词，也可以沿用同一组任务和评分标准再测，判断这次修改是否真正改善了结果。

## 外部反馈让反思有更多依据

反思不必只靠模型“自己想”，而是把代码真的跑一遍，用运行结果或报错来指导他改代码。
课程举了代码运行反馈，以及字数统计、网页搜索、正则表达式匹配等例子：前者告诉模型代码哪里报错；字数统计可以核实长度要求；搜索可带来新资料；正则表达式可检查格式或模式。反馈的价值在于它提供了可供下一轮修改的具体信号。
