# 语音 Agent 如何搭起来：实现路径、组件与实时传输



## 从“能说话”到“能实时对话”

Voice Agent（AI 语音智能体）把语音输入、模型理解与语音输出连接起来，目标是让人与系统持续、自然地对话。

### 两条实现路径
1. **经典串联方案：STT → LLM → TTS。**
   用户语音 → ASR/STT 转成文字 → LLM 或 Agent 工作流推理、必要时调用工具 → TTS 把回复转成语音。
   各组件可以分别选择和调整，开发与定位问题比较直观；代价是多个处理环节可能累积等待时间。
2. **端到端实时方案：Speech-to-Speech。**
   用户音频进入实时语音模型，由模型直接产生音频回复。
   它减少了显式的 STT→文本 LLM→TTS 串联环节；实际延迟、可控程度和可用功能仍取决于模型与系统实现，不能仅凭“端到端”保证更快或更简单。适合实时对话，实现比较简单但提供的功能也有限。

输出主要是语音，也可与视频等表现形式组合。以下笔记重点讨论实时语音交互。

### 串联方案里的组件各做什么

1. **ASR/STT（自动语音识别／语音转文字）**：把音频转录为文字，方向是 audio → text。

2. **LLM 或 LLM Agent**：读取用户问题的转写文字，生成回复；也可以在工作流里完成推理、调用工具，或产生包含图片等形式的结果，核心方向是 text → text。也可以输出多模态回复（示例：文字+图片）

3. **TTS（文字转语音，也称语音合成）**：把回复文字变为人声，方向是 text → audio。

在主链路周围，还需要判断用户是否正在讲话、是否已经讲完：

- **VAD（Voice Activity Detection语音活动检测）**：从音频中判断有没有有效语音活动，帮助系统区分说话/静音/噪音；不宜把它理解为能独自判断一句话的意思。安静时可以减少不必要的后续转写处理，但具体节省程度依系统配置而定。

  例如电话里的背景声或停顿，不必都当成完整用户请求送去识别。只在有人说话时送入ASR，避免噪声误触。

  注意：VAD主要是检测有没有人声，并不等同于降噪。真正过滤背景噪音通常还要配合NS（噪音抑制）、AEC（回声消除）、AGC（自动增益控制）等音频前处理模块。

- **EOU（End of Turn / End of Utterance detection，语句结束检测）**：判断用户这一轮是否说完，再决定何时让 Agent 开始回答。人说话会因语言、习惯和思考而停顿；如果只看到短暂静音就回答，AI 可能抢话。

  例如用户停下来想下一句时，系统还需要判断这是不是发言结束。后文会展开 VAD 与语义信号怎样配合。

## 实时连接与课程代码示例

要降低等待感，可以减少不必要的往返和串行等待，并使用适合实时音频的传输链路。本课程采用 LiveKit：客户端的音频经 WebRTC 连接到 LiveKit 服务器，再由 Agent 参与会话，并非“绕过中间服务器”的纯点对点路径。

课程以 WebRTC 与 WebSocket 搭建实时交互：
1. **WebRTC**：承载实时音频流。在这个 LiveKit 示例里，网页或移动端与 LiveKit 服务器之间通过 WebRTC 传送音频。

2. **WebSocket**：（Web Real-Time Communication）免费开源项目，给网页、移动端 App 提供实时音视频通信 API，用来传输音视频流。客户端（网页 / 手机 / 电话）和 LiveKit 服务器之间靠 WebRTC 传输音频流，低延迟，适合语音通话。在 LiveKit 的客户端协议里用于与服务器交换信令消息，再建立 WebRTC 媒体连接；WebRTC 标准本身并不规定必须用 WebSocket 做信令。

3. **处理方式**
   - 异步和流式处理：尽可能边接收、边转写、边生成，而不是每一步都等完整结果。
   - 管理输入与输出音频流，避免收、发互相阻塞。
   - 按选用的 STT、LLM、TTS 服务能力接入流式接口。

## 音频如何从设备到达 Agent

![课程图：Pasted image 20260910194609.png](图片附件/Pasted%20image%2020260910194609.png)

做架构选择时，要同时考虑“听懂用户并给出合适回复”的质量和交互速度。先看客户端（用户设备）与服务端之间怎样传音频。

IP 之上常见的传输协议有 TCP 与 UDP，它们处理丢包和顺序的方式不同：

![课程图：Pasted image 20260910194758.png](图片附件/Pasted%20image%2020260910194758.png)

1. **TCP 偏重可靠、按序交付。**
   假设发送包 1、2、3，包 1 和 3 先到而包 2 迟到：已经连续收到的包 1 可以先交给应用；包 3 所在的后续字节要等缺失的包 2 补齐，才按序交付。这种等待有助于理解“队头阻塞”。
   对实时语音来说，语音每秒会传输大量音频包。只要少量数据包延迟或者丢失，就会发生排队堵塞，音频卡顿、断音、停顿，用户体验很差。所以 TCP 不适合实时语音 Agent。

![课程图：Pasted image 20260910195043.png](图片附件/Pasted%20image%2020260910195043.png)

2. **UDP 不替应用保证可靠、按序交付。**

   仍以包 1、2、3 为例，应用可能先看到 1 和 3，，包 2 还在路上。Agent 可以直接拿到包 1、包 3。 程序自己做决定：可以等待包 2、忽略丢失包、插值补齐、直接跳过丢包。这给实时媒体留出处理时效与丢包的空间。
   因此实时音频通常优先采用以 UDP 为基础的媒体传输，但补偿、拥塞控制等仍要由其上的协议或系统负责。

UDP 是**底层原始传输协议**，直接使用裸 UDP，需要额外处理连接建立、网络抖动、丢包与安全等问题；浏览器页面也不能像原生程序那样直接开 UDP socket。因此实际开发通常使用更高层的传输方案。
所以使用封装好的高层协议：HTTP、WebSocket、WebRTC。

![课程图：Pasted image 20260910195742.png](图片附件/Pasted%20image%2020260910195742.png)

**这里需要的连接**：用户和 Agent 能持续收发音频，而不是每次都等一问一答完成。因此：需要的架构是在用户和Agent之间建立起持久的连接，并且能够持续不断的来回播放音频。

<img src="图片附件/Pasted%20image%2020260910200510.png" alt="课程图：Pasted image 20260910200510.png" width="312">

课程选择持久、双向的媒体链路，理由在下面的协议比较中更清楚。

1. **HTTP**：通常以请求／响应方式使用。HTTP/1.1 本身支持持久连接，也能传输流式响应；只是传统的一问一答接口不直接提供实时音视频会话所需的一整套能力。
2. **WebSocket**：基于 TCP。持久连接，可以双向持续传文本 / 二进制流。 但底层依旧跑在 TCP 上，一旦数据包丢包或者延迟，后面的数据会卡住。延迟比 WebRTC 高，一般用来传递控制指令、文本消息；它没有默认提供实时音视频所需的抖动缓冲、丢包补偿等媒体能力。
3. **WebRTC**：专门为浏览器、移动端的实时音视频设计。 支持全双工长连接，两端可以双向持续收发数据。帮你封装 UDP 的所有复杂逻辑（数据包排序、丢包补偿、拥塞控制、数据压缩）。 我们前面 LiveKit 语音 Agent，音频传输用的就是 WebRTC。


就本课程要实现的双向、低等待感语音会话而言，WebRTC 是合适的选择；这是一项与场景有关的选型判断。

WebRTC 开发与扩容有一定复杂度，课程选用 LiveKit 承担实时媒体连接与服务器转发工作。
