# 低延迟语音 Agent：分层选型、流式优化与监控

> 

串联方案经过语音转写、文本生成与语音合成。用户感觉到的等待由多个环节共同决定；下面从课程给出的基准出发，走到选型、流式处理与指标采集。

## 为什么实时语音需要关注延迟

语音回复若明显迟到，轮流说话就会显得不自然。因此先看课程给出的比较基准，再看延迟来自哪里。

1. **人类对话参照**：课程图给出 236 ms。这个数值对应英语问答话轮转换的研究样本均值，可帮助建立量级直觉，不能解释为所有人在 236 ms 内“期待”得到答复。
2. **组件延迟示例**：课程图把 VAD、话轮结束、STT、LLM 首 token 和 TTS 首音频的示例耗时相加，得到约 540 ms 的比较值。这是给定配置下的估算，不是语音 Agent 的普遍理论下限；并行和流式处理也会改变简单相加的结果。

### 课程提醒的评估与优化难点

![课程图：Pasted image 20260910164851.png](图片附件/Pasted%20image%2020260910164851.png)

语音 Agent 的评估不只看回答文字，还要留意听、说与网络链路中的问题：

**评估挑战**：
1. **语音流畅性**：ASR/TTS、VAD/话轮检测都可能带来转写错误、停顿误判或语音瑕疵。例如“嗯”、拖长音与自然停顿会影响转写和话轮判断。
2. **跨语言识别**：课程提醒关注多语言 ASR；不同语言与模型的表现需要分别测试，不能笼统断定一定弱于英语。

**延迟优化**


延迟测量比较复杂：还要区分客户端和服务端的测量位置，两端统计结果可能不同。
- LiveKit 负责此示例中的实时传输，但网络耗时仍需测量。

- 在 STT→LLM→TTS 链路中，LLM 可能是主要等待来源之一；也应测量 STT、话轮结束、TTS 与播放，不宜预设瓶颈。
- 本地部署可考虑更小或量化的模型；调用外部 API 则要关注限流和服务商的性能建议。

- 用提示约束较短回答，或先给简短确认语、再分段回答，可以降低用户的主观等待感；这不等于端到端耗时必然减少。

## 从架构理解走向产品选型

<img src="图片附件/Pasted%20image%2020260911151629.png" alt="课程图：Pasted image 20260911151629.png" width="438">

语音系统总要在**延迟、质量、成本**之间做取舍。串联流水线（VAD→STT→话轮判断→LLM→TTS）的一个好处，是可以分别选择各层组件，而不必所有环节绑定同一方案。

<img src="图片附件/Pasted%20image%2020260911151928.png" alt="课程图：Pasted image 20260911151928.png" width="260"><img src="图片附件/Pasted%20image%2020260911152134.png" alt="课程图：Pasted image 20260911152134.png" width="273">

**VAD**语音活动检测

VAD 识别说话与静音，可减少无意义音频进入 STT 的机会，从而降低部分转写误触发和处理量；收益幅度取决于噪声条件、模型和是否持续转写，不能保证“极大降低成本”。

**STT：选择识别能力**
选型要看：①支持哪些语言；②是否需要翻译等其他处理；③是否需要适合窄场景的模型，例如电话音频压缩、信噪比差，可单独测试电话场景 STT。

**LLM：决定回应内容**
负责文本推理和生成回答。若业务需要，可在这一层增加内容安全过滤或其他约束。

**TTS：决定声音呈现**
可选择音色、口音，并是否能设置自定义发音规则（为专业术语或特殊词汇设置发音规则）。

### 让语音流水线边收边处理
课程图把 VAD、话轮检测和 STT 放在同一条输入链路上：
1. **VAD** 判断有没有语音。图中的约 15–20 ms 是此课程示意参数，实际耗时需按实现和设备测量。

2. **话轮检测** 监听用户何时结束；在这个流式示例里，它不需要阻断持续进行的 STT 转写。

3. **STT** 边接收语音边输出文字片段。

课程示例的完整链路是：用户开始说话 → VAD 约 15 ms → 流式转写 → 话轮结束判断约 100 ms → LLM。两个数值都应视为图中的示例，不是各产品的固定耗时。

用户说话时，STT 持续给出片段，话轮检测同时监听；确认这一轮用户发言结束，再把本轮转写交给 LLM。不必先收齐完整音频才启动所有处理。

<img src="图片附件/Pasted%20image%2020260911155741.png" alt="课程图：Pasted image 20260911155741.png" width="380">

LLM 逐 token 生成回复，通常不知道完整回答最终有多长。若 TTS 支持合适的流式输入，可把已经形成的文字片段陆续交给它，不必等整段文本完成。图内箭头指向 TTS，虽有一处英文项目符号写成 STT，这里的文字输出仍应理解为交给 TTS。

**LLM 的 TTFT（Time to First Token）**：从 LLM 请求开始到第一个输出 token 的时间。直接影响了用户要等待多久，才能听到 AI 的第一句话，是语音 Agent 延迟优化最核心的指标。但用户第一次听到声音还要经过 TTS、传输和播放，不能只由 TTFT 决定。

在要缩短首句等待时间时，TTFT 值得重点测量，同时要看话轮结束、TTS 首音频和客户端播放。

<img src="图片附件/Pasted%20image%2020260911160236.png" alt="课程图：Pasted image 20260911160236.png" width="379">

LLM 输出的文字片段陆续交给 TTS，有机会让文本生成和语音合成重叠，减少首句等待。是否能流畅播放仍取决于片段切分、合成速度和网络。

至于完整音频的总渲染时长反而没有那么重要。
因为：AI 把语音播放出来本身就需要时间，这个播放过程天然充当了缓冲区 (buffer)。 只要 TTS 生成音频的速度，**比 AI 朗读播放的速度更快**就没问题。**所以优化 TTS 性能，重点就是压低 TTFB，决定用户多快听到 AI 开口。**

完整音频的生成时长也不能忽略：如果 TTS 赶不上播放进度，就可能停顿；如果能够持续快于播放，首段音频出现的时间更直接影响开口等待感。

**TTS 的 TTFB（Time to First Byte首音频字节时间）** 是从 TTS 开始处理到生成第一段音频字节的时间，也就是用户**第一次听到 AI 声音**的时间点。这是 TTS 最关键指标。属于模型／服务侧指标，并不等于用户设备第一次播出声音的时刻。后者还包括后续传输、缓冲与播放。

**Rendering Time（渲染时间 real latency）** 是生成整段音频所用的时间。它与 TTFB 应一起看：首段快但后续供给不稳，仍会影响用户体验。

## 怎样观察系统瓶颈

为 VAD、STT、话轮判断、LLM 和 TTS 记录耗时与日志，才能区分等待到底发生在哪一段。客户端听到声音的时间还应结合客户端侧测量。

课程归纳的四类指标：

1. LLM Metrics
    - Prompt Tokens：输入token数量
    - Completion Tokens：模型生成输出token数量
    - Tokens per second：模型每秒生成token速度
    - TTFT：首 token 耗时，反映 LLM 开始输出的速度。
2. STT Metrics
    - Duration：STT转写耗时
    - Audio Duration：用户原始语音时长
    - Streamed：是否开启STT流式转写
3. End-of-utterance Metrics（话轮结束指标）
    - VAD语音检测耗时
    - STT转写耗时
4. TTS Metrics
    - TTFB：TTS 生成第一段音频字节的耗时。
    - Duration：TTS渲染音频耗时
    - Audio Duration：AI语音播放总时长
    - Streamed：是否开启TTS流式合成
